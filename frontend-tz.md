# Техническое задание: Market Analyzer — фронтенд

**Проект:** веб-интерфейс сервиса аналитики биржевых данных
**Версия ТЗ:** 1.0
**Связанные документы:** `market-analyzer-architecture.md`, `market-analyzer-tz.md`

---

## 1. Цели

Интерфейс для просмотра рыночных данных и аналитики: графики свечей с
индикаторами, live-поток сделок, панели аномалий и корреляций.

Главное требование — **скорость**. Это плотный дашборд с высокочастотными
обновлениями и графиками на десятки тысяч точек. Всё остальное подчинено этому.

| № | Цель | Измеримый критерий |
|---|---|---|
| Ц1 | Мгновенная загрузка | LCP < 1.2 с на десктопе, TTI < 1.8 с |
| Ц2 | Плавность при интеракции | 60 fps при панорамировании и зуме графика |
| Ц3 | Живые данные без деградации | 1000 WS-сообщений/сек без пропуска кадров |
| Ц4 | Малый вес | Начальный JS-бандл < 150 КБ gzip |
| Ц5 | Плотная, читаемая подача данных | Работоспособность от 1280×720 без горизонтального скролла |

### Вне области работ

- Мобильная вёрстка как первоклассный сценарий (достаточно, чтобы не ломалось)
- Авторизация, мультипользовательский режим, настройки профиля на сервере
- Размещение реальных ордеров
- SSR / SEO — это внутренний инструмент, рендерим на клиенте
- Поддержка браузеров без WebGL/`OffscreenCanvas` и IE/legacy Edge

## 2. Стек и обоснование

### 2.1 Итоговый набор

| Слой | Выбор | Почему |
|---|---|---|
| Фреймворк | **SolidJS** | Нет виртуального DOM, гранулярная реактивность через сигналы. При потоке WS-сообщений обновляется ровно тот DOM-узел, который изменился, без диффинга дерева. Рантайм ~7 КБ gzip |
| Сборка | **Vite** | Мгновенный dev-сервер, esbuild/Rollup под капотом, встроенное code splitting |
| Язык | **TypeScript** (strict) | Контракты API типизируются, схемы данных из бэкенда переносятся в типы |
| Ценовой график | **TradingView Lightweight Charts** | Canvas-рендер, сделан именно под финансовые графики: свечи, объём, крестовина, автомасштаб. ~45 КБ gzip, Apache 2.0 |
| Графики индикаторов | **uPlot** | Самый быстрый canvas-график для временных рядов, держит сотни тысяч точек. ~20 КБ gzip |
| Транспорт данных | **Apache Arrow IPC** (`apache-arrow`) | Ключевое решение, см. 2.2 |
| Кэш запросов | **@tanstack/solid-query** | Дедупликация, инвалидация, фоновое обновление — не надо писать своё |
| Стили | **Tailwind CSS 4** | Никакого рантайма, только сгенерированный CSS. Быстро строить плотные сетки дашборда |
| Виртуализация | **@tanstack/solid-virtual** | Тейп сделок — это тысячи строк, рендерим только видимые |
| Числа | **decimal.js-light** | Только там, где нужна точная арифметика (см. 2.3) |
| Иконки | **lucide** (по мере надобности, tree-shaken) | |
| Тесты | **Vitest** + **Playwright** | Юниты и e2e/визуальные регрессии |

Версии зависимостей зафиксировать на актуальные мажорные на момент старта —
перед установкой проверить, что мажоры не разошлись.

**Альтернатива фреймворку:** Svelte 5 (runes) — сопоставим по скорости и весу,
компилируется в прямые DOM-операции. Выбор между Solid и Svelte — вопрос
предпочтения; React в этом проекте проигрывает из-за оверхеда VDOM на
высокочастотных обновлениях.

### 2.2 Почему Arrow, а не JSON

Бэкенд уже работает на Arrow и Parquet (DuckDB внутри — колоночный). Отдавать
данные наружу как JSON означает: сериализовать колонки в текст, прогнать
`JSON.parse` на клиенте, собрать объекты, потом снова разложить в типизированные
массивы для графика. На 50 000 свечей это десятки миллисекунд парсинга и
кратный расход памяти.

Arrow IPC вместо этого отдаёт готовые бинарные колонки: клиент получает
`Float64Array` / `BigInt64Array` практически без обработки и передаёт их прямо в
canvas-график.

**Требование к бэкенду:** эндпоинты, возвращающие ряды, поддерживают
`Accept: application/vnd.apache.arrow.stream` и отдают Arrow IPC stream. JSON
остаётся как fallback и для отладки.

### 2.3 Точность чисел

Бэкенд хранит цены как `DECIMAL(18,8)`. В JS нет нативного decimal, а `number` —
это `f64`.

Правило:
- **Отрисовка графиков и осей** — `f64` допустим. Пиксельная сетка всё равно
  грубее, чем 8 знаков после точки.
- **Любая арифметика над деньгами, которую видит пользователь как число**
  (P&L, суммы, спреды в б.п.) — только через `decimal.js-light`, из строкового
  представления, без промежуточного приведения к `number`.
- Arrow-колонки типа `Decimal128` читаются как строки/BigInt, а не как float.

### 2.4 Опционально: DuckDB-WASM

`@duckdb/duckdb-wasm` позволяет держать полученный Arrow-набор в браузере и
пересчитывать агрегаты локально: сменил таймфрейм с 1m на 15m — ресемплинг
происходит на клиенте за миллисекунды, без запроса к серверу.

Ограничение: бандл в несколько мегабайт. Поэтому — **только ленивая загрузка по
явному действию пользователя** («режим исследования»), никогда не в начальном
чанке. Вынесено в Этап 5 как необязательное.

## 4. Функциональные требования

### 4.1 Слой данных

**FR-1.1 — Arrow-клиент**
Все табличные запросы идут с `Accept: application/vnd.apache.arrow.stream`.
Ответ читается через `tableFromIPC`, колонки извлекаются как типизированные
массивы без промежуточного маппинга в массив объектов.

**FR-1.2 — Fallback на JSON**
При ответе `406` или `Content-Type: application/json` клиент прозрачно
переключается на JSON-парсинг. Факт фолбэка пишется в консоль в dev-режиме.

**FR-1.3 — Кэширование**
Запросы кэшируются по ключу `(endpoint, symbol, interval, from, to, params)`.
Повторный выбор ранее просмотренного диапазона данных не вызывает сетевого
запроса, если данные не устарели (`staleTime` для исторических диапазонов —
бесконечность, для текущего дня — 30 с).

**FR-1.4 — Отмена запросов**
При смене символа или диапазона незавершённые запросы отменяются через
`AbortController`. Ответ отменённого запроса не должен попадать в UI.

**FR-1.5 — Обработка ошибок**
Формат ошибок бэкенда (`{ error: { code, message, details } }`) разбирается и
показывается человекочитаемо. Ошибка одной панели не ломает остальные —
каждая панель обёрнута в границу ошибки со своим состоянием и кнопкой повтора.

### 4.2 Live-поток

**FR-2.1 — Подключение**
WebSocket к `/stream/{symbol}` при выборе символа. При смене символа старое
соединение закрывается.

**FR-2.2 — Реконнект**
При обрыве — переподключение с экспоненциальным бэкоффом (база 500 мс,
множитель 2, максимум 15 с, без ограничения числа попыток). Состояние
соединения (`connecting` / `live` / `reconnecting` / `offline`) отображается
индикатором в интерфейсе.

**FR-2.3 — Батчинг обновлений — критично для производительности**
Входящие сообщения складываются в буфер. Применение к UI происходит **один раз
за кадр** через `requestAnimationFrame`. Сигнал не обновляется на каждое
сообщение — иначе при 1000 msg/сек получим 1000 перерисовок в секунду.

**FR-2.4 — Ограничение буфера**
Тейп сделок хранит не более 500 последних записей в памяти, старые вытесняются.
Буфер обновлений при переполнении (> 5000 необработанных сообщений) сбрасывает
промежуточные значения, оставляя последнее состояние — деградируем в частоте,
а не в отзывчивости.

**FR-2.5 — Пауза при неактивной вкладке**
При `document.hidden` обновление графика приостанавливается, при возврате —
данные догружаются одним REST-запросом, а не проигрыванием накопленной очереди.

### 4.3 Ценовой график

**FR-3.1 — Свечи**
Отрисовка OHLCV через Lightweight Charts: свечной ряд + гистограмма объёма на
отдельной шкале.

**FR-3.2 — Интеракция**
Панорамирование, зум колесом и жестом, крестовина с подсказкой значений,
автоподгонка масштаба, кнопка возврата к текущему моменту.

**FR-3.3 — Инкрементальное обновление**
Приход новой свечи обновляет только последнюю точку через `update()`.
Полная перезапись серии (`setData`) допустима только при смене символа,
интервала или диапазона.

**FR-3.4 — Индикаторы на основном графике**
Наложение линейных серий: VWAP, скользящие средние. Состав переключается
пользователем, набор сохраняется локально.

**FR-3.5 — Догрузка истории**
При прокрутке к левому краю подгружается предыдущий диапазон и добавляется в
начало серии без сброса позиции просмотра.

**FR-3.6 — Пустое состояние**
Если данных по символу нет — понятное сообщение, а не пустой прямоугольник.

### 4.4 Панели индикаторов

**FR-4.1 — Отдельные панели**
Под ценовым графиком — независимые панели на uPlot: реализованная
волатильность, OFI, z-score объёма.

**FR-4.2 — Синхронизация оси времени**
Все панели используют общий видимый диапазон. Зум/панорамирование в любой панели
или на основном графике синхронно применяется ко всем остальным. Крестовина
синхронизирована по горизонтали.

**FR-4.3 — Управление составом**
Панели можно включать и выключать; отключённая панель не подписана на данные
и не запрашивает их с сервера.

### 4.5 Панель аномалий

**FR-5.1** Таблица аномалий объёма из `/analytics/{symbol}/anomalies`:
время, цена, объём, z-score. Сортировка по времени и по z-score.

**FR-5.2** Порог z-score и размер окна настраиваются в UI; изменение
перезапрашивает данные с дебаунсом 300 мс.

**FR-5.3** Клик по строке перемещает основной график к соответствующему моменту
и подсвечивает свечу маркером.

### 4.6 Матрица корреляций

**FR-6.1** Тепловая карта попарных корреляций для выбранного набора символов
из `/analytics/correlation`.

**FR-6.2** Диапазон значений отображается расходящейся цветовой шкалой с нулём
в нейтральном цвете. Числовые значения — в ячейках, при достаточном размере.

**FR-6.3** Цвет не является единственным носителем информации: значение
дублируется текстом (доступность).

### 4.7 Тейп сделок

**FR-7.1** Виртуализованный список последних сделок: время, цена, объём,
сторона агрессора.

**FR-7.2** Рендерятся только видимые строки. При 500 элементах в памяти в DOM
находится не более ~30 узлов.

**FR-7.3** Автоскролл к новым сделкам, отключается при ручной прокрутке вверх
и возобновляется кнопкой.

### 4.8 Оболочка интерфейса

**FR-8.1 — Выбор символа**
Поиск с фильтрацией по реестру из `/symbols`, клавиатурная навигация,
недавно использованные наверху.

**FR-8.2 — Строка состояния**
Текущая цена, изменение за 24 ч, объём, статус соединения, метка времени
последнего обновления.

**FR-8.3 — URL как состояние**
Символ, интервал и диапазон отражаются в query-параметрах. Ссылку можно
скопировать и открыть в том же виде. Кнопки «назад/вперёд» браузера работают.

**FR-8.4 — Локальные настройки**
Тема, состав индикаторов и панелей сохраняются в `localStorage`.

**FR-8.5 — Горячие клавиши**
`/` — поиск символа, `1`…`6` — переключение интервала, `Esc` — закрыть
оверлей, `r` — сброс масштаба графика.

## 5. Визуальный дизайн

**DR-1 — Тёмная тема по умолчанию**
Профессиональный трейдинг-интерфейс: тёмный фон, высокая плотность информации.
Светлая тема — вторична, но обе строятся на одном наборе токенов.

**DR-2 — Токены, не значения**
Все цвета, отступы, радиусы и типографика — через CSS-переменные в
`tokens.css`. Хардкод hex-значений в компонентах не допускается.

**DR-3 — Типографика**
Числовые данные — моноширинным шрифтом с табличными цифрами
(`font-variant-numeric: tabular-nums`), чтобы значения не «прыгали» при
обновлении. Интерфейсный текст — системный sans-serif стек, без загрузки
веб-шрифтов в критическом пути.

**DR-4 — Семантика цвета**
Рост/падение задаются токенами, а не прямыми «зелёный/красный». В настройках —
альтернативная палитра для дальтоников (синий/оранжевый).

**DR-5 — Сдержанная анимация**
Переходы только на смене состояний интерфейса, длительность ≤ 150 мс.
Никаких анимаций на потоке данных — цифры меняются мгновенно. Уважать
`prefers-reduced-motion`.

**DR-6 — Скелетоны, не спиннеры**
Загрузка показывается каркасом будущего содержимого, чтобы layout не
дёргался. Отсутствие сдвигов компоновки — измеримое требование (см. NFR-1.6).

**DR-7 — Плотность**
Целевая компоновка: основной график ~55% высоты, панели индикаторов ~25%,
боковая колонка с тейпом и аномалиями. Минимальная рабочая ширина 1280 px.

## 7. Контракт с бэкендом

Требуется добавить к бэкенду (расширение раздела 3.5 серверного ТЗ):

**BE-1** Поддержка `Accept: application/vnd.apache.arrow.stream` на всех
эндпоинтах, возвращающих ряды: `/ohlcv/*`, `/analytics/*`.

**BE-2** CORS для dev-origin (`http://localhost:5173`), настраиваемый через
конфиг.

**BE-3** Заголовки кэширования: `Cache-Control: public, max-age=31536000,
immutable` для завершённых исторических диапазонов; `no-cache` для диапазонов,
включающих текущий незакрытый период.

**BE-4** Сжатие ответов (gzip/br) для JSON-фолбэка. Arrow-поток — по
усмотрению, замерить выигрыш.

**BE-5** WS-протокол `/stream/{symbol}`: сообщения в JSON с полем `type`
(`trade` / `kline` / `heartbeat`). Heartbeat не реже раза в 30 с, чтобы клиент
отличал тишину от обрыва.

**BE-6** Эндпоинт `/symbols` отдаёт `price_precision` и `qty_precision` по
каждому инструменту — для корректного форматирования чисел на клиенте.

## 8. Этапы и приёмка

### Этап 1 — Каркас и ценовой график

Vite + Solid + TS + Tailwind, layout-оболочка, Arrow-клиент, Lightweight Charts

- NFR-1.1 и NFR-1.3 замерены и выполнены
- URL отражает выбранный символ и интервал (FR-8.3)

### Этап 2 — Индикаторы и синхронизация

Панели на uPlot, синхронизация видимого диапазона, наложения VWAP/MA,
догрузка истории при прокрутке.

Приёмка:
- Зум в любой панели синхронно применяется ко всем (FR-4.2)
- Прокрутка к левому краю догружает историю без сброса позиции (FR-3.5)
- NFR-1.4: профиль без длинных задач при интеракции

### Этап 3 — Live-режим

WebSocket, реконнект, батчинг через rAF, тейп сделок, инкрементальное
обновление графика, индикатор состояния соединения.

Приёмка:
- NFR-1.5: нагрузочный мок на 1000 msg/сек, fps не падает ниже 55
- Принудительный обрыв соединения → реконнект → данные догружены без разрыва
- NFR-1.7: час работы, рост heap в пределах нормы
- Обновление свечи идёт через `update()`, не через `setData()` — подтвердить
  профилем

### Этап 4 — Аналитические панели

Аномалии, матрица корреляций, строка состояния, горячие клавиши, границы
ошибок, скелетоны.

Приёмка:
- Клик по аномалии перемещает график к моменту (FR-5.3)
- Отказ одного эндпоинта не ломает остальные панели (FR-1.5)
- NFR-1.6: CLS < 0.05
- Полный проход по интерфейсу с клавиатуры (NFR-3.1)

### Этап 5 — Полировка и опции

Светлая тема, палитра для дальтоников, экспорт данных, Lighthouse CI в
пайплайне. Опционально: DuckDB-WASM для локального ресемплинга.

Приёмка:
- Lighthouse Performance ≥ 95, Accessibility ≥ 95
- Все NFR раздела 6 подтверждены замерами, результаты сведены в отчёт
- DuckDB-WASM (если делаем) грузится только по явному действию — проверить,
  что в начальном чанке его нет

## 9. Тестирование

| Уровень | Что покрывается | Инструмент |
|---|---|---|
| Юнит | Чтение Arrow-колонок, форматирование чисел и времени, логика бэкоффа, батчинг буфера | Vitest |
| Компонентные | Панели с замоканными данными, состояния загрузки и ошибки | Vitest + `@solidjs/testing-library` |
| E2E | Сценарии: выбор символа → загрузка → зум → live → аномалия → переход | Playwright |
| Визуальные регрессии | Скриншоты ключевых экранов в обеих темах | Playwright snapshots |
| Производительность | NFR-1.1…1.6 в CI, сборка падает при превышении бюджета бандла | Lighthouse CI + скрипт проверки размера |

WS-нагрузка тестируется локальным мок-сервером с настраиваемой частотой
сообщений — реальная биржа для этого не нужна.

## 10. Риски

| Риск | Влияние | Митигация |
|---|---|---|
| Обновления на каждое WS-сообщение | Критическое: интерфейс встанет | Батчинг через rAF (FR-2.3) заложен с самого начала, не как оптимизация потом |
| `setData()` вместо `update()` на каждой свече | Высокое: перерисовка всей серии | Явное требование FR-3.3, проверяется профилем в приёмке Этапа 3 |
| Потеря точности цен на `f64` | Среднее | Правило раздела 2.3, decimal только в арифметике |
| Раздувание бандла зависимостями | Среднее | Бюджет в CI (NFR-1.1), динамические импорты тяжёлого |
| Утечка памяти в live-режиме | Среднее | Ограничение буферов (FR-2.4), проверка NFR-1.7 |
| Бэкенд не успеет с Arrow-эндпоинтами | Низкое | Фолбэк на JSON (FR-1.2) позволяет разрабатывать параллельно |
