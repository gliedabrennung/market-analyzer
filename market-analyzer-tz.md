# Техническое задание: Market Analyzer

**Проект:** сервис сбора и аналитики биржевых данных
**Стек:** Rust (edition 2021, MSRV 1.80) + DuckDB + Apache Parquet
**Версия ТЗ:** 1.0
**Связанный документ:** `market-analyzer-architecture.md`

---

## 1. Цели и назначение

### 1.1 Назначение

Система собирает публичные рыночные данные с криптобирж, сохраняет их в
колоночном формате и предоставляет аналитические расчёты через CLI и HTTP API.

### 1.2 Цели

| № | Цель | Измеримый критерий |
|---|---|---|
| Ц1 | Непрерывный сбор данных без потерь | Пропуски в потоке < 0.1% свечей за сутки работы |
| Ц2 | Быстрая аналитика на исторических данных | Запрос агрегата за 30 дней по 1 символу < 500 мс |
| Ц3 | Компактное хранение | Коэффициент сжатия к сырому JSON ≥ 8× |
| Ц4 | Расширяемость на новые биржи | Добавление биржи = реализация одного трейта, без правок в других модулях |

### 1.3 Вне области работ (out of scope)

- Исполнение реальных ордеров, работа с приватными API-ключами
- Хранение персональных данных пользователей, авторизация
- Приватные данные аккаунта (баланс, позиции)
- Высокочастотная торговля, требования к latency ниже 10 мс
- Полноценный фронтенд-фреймворк (допускается статическая страница)

## 2. Термины

| Термин | Определение |
|---|---|
| **Kline / свеча** | OHLCV-агрегат за фиксированный интервал |
| **Trade / тик** | Единичная сделка: время, цена, объём, сторона агрессора |
| **Символ** | Торговая пара, например `BTCUSDT` |
| **Backfill** | Загрузка исторических данных через REST |
| **Compaction** | Склейка мелких Parquet-файлов одной партиции в один |
| **OFI** | Order Flow Imbalance, дисбаланс потока заявок |
| **Партиция** | Каталог вида `symbol=BTCUSDT/dt=2026-09-05` |

## 3. Функциональные требования

### 3.1 Модуль сбора данных (`exchanges`)

**FR-1.1 — Абстракция биржи**
Определить трейт `ExchangeSource` с методами получения метаданных инструментов,
исторических свечей и подписки на поток. Реализовать для Binance Spot.

**FR-1.2 — Историческая загрузка**
Загрузка свечей за произвольный диапазон дат с автоматической пагинацией.
Интервалы: `1m`, `5m`, `15m`, `1h`, `4h`, `1d`.

**FR-1.3 — Соблюдение лимитов**
Учёт весовой модели лимитов биржи. При `HTTP 429` — экспоненциальный бэкофф
(база 1 с, множитель 2, максимум 60 с, до 5 попыток). При `418` — пауза не менее
времени из заголовка `Retry-After`.

**FR-1.4 — Live-поток**
Подписка на combined stream по списку символов. Поддержка типов событий:
`trade`, `kline`, `depthUpdate`.

**FR-1.5 — Устойчивость соединения**
При обрыве WebSocket: переподключение с бэкоффом, затем **обязательный REST-добор
данных** за период простоя. Факт добора логируется с указанием интервала.

**FR-1.6 — Нормализация**
Все события приводятся к внутренним типам `Trade` / `Kline` / `DepthUpdate`
независимо от биржи-источника. Метки времени — UTC.

### 3.2 Модуль хранения (`storage`)

**FR-2.1 — Формат и layout**
Данные пишутся в Parquet со сжатием zstd, hive-партиционирование:
`data/{dataset}/symbol={symbol}/dt={YYYY-MM-DD}/part-{NNNN}.parquet`

**FR-2.2 — Батчинг записи**
Флаш буфера по достижении **любого** из порогов: 50 000 строк или 30 секунд.
Пороги конфигурируемы.

**FR-2.3 — Дедупликация**
Перед записью — отсев дублей по ключу `(symbol, trade_id)` для сделок и
`(symbol, interval, open_time)` для свечей. Повторный backfill того же диапазона
не должен приводить к дублированию строк в результатах запросов.

**FR-2.4 — Типы денежных величин**
Цены и объёмы хранятся как `DECIMAL(18,8)` / `DECIMAL(28,8)`. Использование
`f64` для денежных величин недопустимо.

**FR-2.5 — Compaction**
CLI-команда, склеивающая все `part-*.parquet` указанной партиции в один файл.
Операция атомарна: запись во временный файл, затем замена; при ошибке исходные
файлы остаются нетронутыми.

**FR-2.6 — Метабаза**
Файл `meta.duckdb` хранит: реестр символов, состояние коллектора (последняя
загруженная метка времени по каждому символу и интервалу), версию схемы,
зарегистрированные view поверх Parquet.

**FR-2.7 — Миграции**
Схема метабазы версионируется. При старте приложение проверяет версию и
применяет недостающие миграции; при несовместимой версии — завершение с
понятной ошибкой.

### 3.3 Аналитический модуль (`analytics`)

Все расчёты выполняются средствами DuckDB SQL. Ручная реализация оконных функций
на Rust не допускается.

**FR-3.1 — Ресемплинг**
Построение OHLCV любого таймфрейма из сырых сделок через `time_bucket`.

**FR-3.2 — VWAP**
Скользящий VWAP с настраиваемым окном (по умолчанию 20 периодов).

**FR-3.3 — Реализованная волатильность**
На логарифмических доходностях, с приведением к дневному масштабу.

**FR-3.4 — Аномалии объёма**
Z-score объёма относительно скользящего окна (по умолчанию 100 периодов,
порог 3.0). Окно и порог — параметры запроса.

**FR-3.5 — Order Flow Imbalance**
Разность объёмов покупок и продаж по агрессору, нормированная на суммарный
объём, с группировкой по бакетам времени.

**FR-3.6 — Корреляции**
Попарная корреляция логдоходностей для набора символов на общей временной сетке.

**FR-3.7 — Межбиржевой спред**
Сопоставление рядов с разными метками времени через `ASOF JOIN`, расчёт спреда
в абсолютном выражении и в базисных пунктах.

**FR-3.8 — Организация запросов**
SQL хранится в отдельных `.sql`-файлах, подключается через `include_str!`.
Параметры передаются только через prepared statements. **Конкатенация строк для
подстановки пользовательского ввода в SQL запрещена.**

### 3.4 CLI (`cli`)

**FR-4.1** Команды:

```
market-analyzer backfill  --symbol <SYM>... --interval <INT> --from <DATE> [--to <DATE>]
market-analyzer stream    --symbol <SYM>... [--dataset trades|klines]
market-analyzer query     --name <QUERY> --symbol <SYM> [--param k=v]... [--format table|json|csv]
market-analyzer compact   [--symbol <SYM>] [--date <DATE>]
market-analyzer symbols   [--refresh]
market-analyzer serve     [--port <PORT>]
```

**FR-4.2** Вывод результатов в форматах: таблица (по умолчанию), JSON, CSV.

**FR-4.3** Флаг `--verbose` повышает уровень логирования; `--config <PATH>`
указывает файл конфигурации.

### 3.5 HTTP API (`api`)

**FR-5.1** Эндпоинты:

| Метод | Путь | Описание |
|---|---|---|
| GET | `/health` | Статус сервиса, версия, время работы |
| GET | `/symbols` | Список доступных символов |
| GET | `/ohlcv/{symbol}` | Свечи. Параметры: `interval`, `from`, `to`, `limit` |
| GET | `/analytics/{symbol}/vwap` | Параметр: `window` |
| GET | `/analytics/{symbol}/volatility` | Параметр: `window` |
| GET | `/analytics/{symbol}/anomalies` | Параметры: `window`, `threshold` |
| GET | `/analytics/{symbol}/ofi` | Параметр: `bucket` |
| GET | `/analytics/correlation` | Параметр: `symbols` (список через запятую) |
| WS | `/stream/{symbol}` | Проброс live-событий |

**FR-5.2 — Формат ошибок**
Единый JSON: `{ "error": { "code": "...", "message": "...", "details": {...} } }`.
Коды HTTP: `400` — невалидные параметры, `404` — неизвестный символ,
`429` — превышен лимит запросов, `500` — внутренняя ошибка.

**FR-5.3 — Валидация**
Все входные параметры валидируются до обращения к БД: символ проверяется по
реестру, диапазон дат — на корректность и максимальную ширину, числовые
параметры — на границы.

**FR-5.4 — Неблокирующее выполнение**
Синхронные вызовы DuckDB выполняются через `spawn_blocking`. Блокировка
async-рантайма недопустима.

**FR-5.5 — Пагинация**
Эндпоинты, возвращающие ряды, поддерживают `limit` (по умолчанию 1000,
максимум 10 000) и `offset`.

### 3.6 Конфигурация и наблюдаемость

**FR-6.1** Конфигурация из файла (TOML) с переопределением через переменные
окружения с префиксом `MA_`. Секретов в репозитории быть не должно.

**FR-6.2** Структурированное логирование через `tracing`, вывод в JSON в
продакшн-режиме. Каждый запрос к API логируется с длительностью и статусом.

**FR-6.3** Метрики в формате Prometheus на `/metrics`: количество принятых
событий, размер буфера, число реконнектов, длительность запросов (гистограмма),
количество ошибок по типам.

**FR-6.4** Graceful shutdown по `SIGINT`/`SIGTERM`: флаш буферов, закрытие
соединений, завершение в течение 10 секунд.

## 4. Нефункциональные требования

### 4.1 Производительность

| № | Требование |
|---|---|
| NFR-1.1 | Пропускная способность ingest: ≥ 10 000 событий/сек на одном ядре |
| NFR-1.2 | Аналитический запрос за 30 дней 1m-свечей (≈43 000 строк): p95 < 500 мс |
| NFR-1.3 | Матрица корреляций для 10 символов за 7 дней: < 3 с |
| NFR-1.4 | Потребление памяти в режиме стриминга 20 символов: < 512 МБ RSS |
| NFR-1.5 | Backfill 1 года 1m-свечей по одному символу: < 5 минут |

### 4.2 Надёжность

| № | Требование |
|---|---|
| NFR-2.1 | Аварийное завершение процесса не приводит к порче Parquet-файлов: недописанные файлы отбрасываются при следующем старте |
| NFR-2.2 | При недоступности биржи сервис продолжает обслуживать аналитические запросы по накопленным данным |
| NFR-2.3 | Повторный запуск любой команды идемпотентен — повторный backfill не портит данные |

### 4.3 Качество кода

| № | Требование |
|---|---|
| NFR-3.1 | Сборка без предупреждений: `cargo clippy -- -D warnings` |
| NFR-3.2 | Форматирование: `cargo fmt --check` |
| NFR-3.3 | Покрытие тестами модулей `analytics` и `storage` ≥ 70% |
| NFR-3.4 | `unwrap()` / `expect()` в библиотечном коде запрещены; допустимы в тестах и при старте приложения с осмысленным сообщением |
| NFR-3.5 | Ошибки: `thiserror` в библиотеках, `anyhow` в бинарниках |
| NFR-3.6 | Публичные API-элементы документированы doc-комментариями |

### 4.4 Ограничения архитектуры

| № | Требование |
|---|---|
| NFR-4.1 | Файл DuckDB открывается на запись **ровно одним** процессом; читающие процессы открывают базу в режиме `read_only` |
| NFR-4.2 | Приложение не требует внешних сервисов (СУБД, брокеров) — только файловая система |
| NFR-4.3 | Сборка проходит на Linux и macOS; DuckDB подключается с `features = ["bundled"]` |

## 6. Этапы работ и приёмка

### Этап 1 — Ядро и backfill

**Результат:** CLI-команда `backfill` создаёт корректные Parquet-файлы.

Приёмка:
- `backfill --symbol BTCUSDT --interval 1m --from 2026-08-01 --to 2026-08-31`
  отрабатывает без ошибок
- В `data/klines/` создана корректная партиционная структура
- `SELECT count(*) FROM read_parquet(...)` возвращает ожидаемое число свечей
  (44 640 для августа) без пропусков и дублей
- Повторный запуск той же команды не увеличивает количество строк

### Этап 2 — Аналитика

**Результат:** библиотека запросов из раздела 3.3.

Приёмка:
- Каждый запрос из FR-3.1…FR-3.7 реализован и вызывается через CLI `query`
- Юнит-тесты на синтетическом наборе: для входа с известным ответом расчёты
  VWAP, волатильности и z-score совпадают с эталоном с точностью 1e-6
- Выполнено NFR-1.2

### Этап 3 — Live-поток

**Результат:** команда `stream` пишет данные в реальном времени.

Приёмка:
- Непрерывная работа 12 часов без утечек памяти (RSS стабилен ±10%)
- Принудительный разрыв соединения приводит к реконнекту и добору данных;
  в результирующем наборе нет пропусков
- Выполнены NFR-1.1 и NFR-1.4

### Этап 4 — API

**Результат:** работающий HTTP-сервис.

Приёмка:
- Все эндпоинты из FR-5.1 отвечают корректно
- Невалидные параметры дают `400` с описанием ошибки, а не `500`
- Нагрузочный тест 100 RPS на `/ohlcv` держится без роста ошибок
- `/metrics` отдаёт метрики в формате Prometheus

### Этап 5 — Эксплуатация и полировка

**Результат:** compaction, документация, бенчмарки.

Приёмка:
- `compact` уменьшает число файлов партиции до одного, данные не изменились
  (контрольная сумма агрегатов до и после совпадает)
- README с инструкцией запуска и примерами команд
- Отчёт с замерами: размер до/после compaction, время запросов до/после
- CI: сборка, `fmt`, `clippy`, тесты

## 7. Тестирование

| Уровень | Что покрывается |
|---|---|
| Юнит | Парсинг ответов бирж, нормализация типов, дедупликация, расчёт бэкоффа |
| Интеграционные | Полный цикл запись → чтение → аналитика на временном каталоге |
| Аналитические | Сверка результатов SQL с эталонными значениями на фиксированном наборе |
| Контрактные | Проверка формы ответов API против зафиксированных схем |
| Нагрузочные | Проверка NFR-1.1, NFR-1.2, NFR-1.4 |

Тестовые данные — фиксированный набор Parquet-файлов в `tests/fixtures/`,
сгенерированный детерминированно. Тесты не должны обращаться к сети;
ответы биржи в юнит-тестах подменяются заранее сохранёнными фикстурами.

## 8. Риски

| Риск | Влияние | Митигация |
|---|---|---|
| Изменение схемы ответов биржи | Высокое | Изоляция парсинга в модуле `exchanges`, контрактные тесты на фикстурах |
| Бан IP по превышению лимитов | Среднее | Лимитер, бэкофф, конфигурируемая пауза между запросами |
| Деградация запросов на объёме данных | Среднее | Партиционирование, compaction, ранняя фильтрация по партиционным ключам |
| Конкурентный доступ к DuckDB-файлу | Среднее | Одно пишущее подключение, read-only для остальных (NFR-4.1) |
| Долгая первая сборка из-за `bundled` DuckDB | Низкое | Кэширование артефактов в CI |
