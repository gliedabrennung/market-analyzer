# Market Analyzer — фронтенд

Дашборд для просмотра рыночных данных и аналитики поверх `market-analyzer`
(см. корневой `README.md`). ТЗ: `../frontend-tz.md`. Реализованы **Этап 1**
— **Этап 5** (§8, полностью — см. "NFR: результаты измерений" ниже): каркас, ценовой
график, Arrow-транспорт, выбор символа/интервала, URL как состояние,
VWAP/MA(20) поверх графика, панели индикаторов на uPlot (волатильность,
OFI, z-score объёма), синхронизация зума между всеми графиками, догрузка
истории при скролле влево, живой WebSocket-поток (реконнект с бэкоффом,
батчинг через rAF, инкрементальное обновление свечи через `update()`,
виртуализированный тейп сделок), таблица аномалий (сортировка, дебounced
порог/окно, клик → прыжок графика к бару с маркером), матрица корреляций
(диврегирующая цветовая шкала + число в каждой ячейке), строка состояния
(цена/24ч-изменение/24ч-объём/соединение/время обновления), горячие
клавиши (`/`, `1`-`6`, `Esc`, `r`), клавиатурная навигация по поиску
символа с недавно использованными, светлая тема, палитра для дальтоников,
экспорт данных в CSV и Lighthouse CI (Performance/Accessibility ≥ 95,
подтверждено замерами — см. "NFR: результаты измерений" ниже).

## Требования

- Node.js — минимум как у Vite (`^20.19.0 || >=22.12.0`); проверено на
  20.20.2. `npm` в этой версии Node ругается баннером про неподдерживаемую
  версию — безвредно, это про сам `npm`, не про наш код.
- Тестовый тулчейн (`vitest`, `@testing-library/jest-dom`, `jsdom`) пока
  зафиксирован на последних мажорах, которые ещё **не** требуют Node 22+
  (`vitest@3`, `jest-dom@6`, `jsdom@25`) — их следующие мажоры уже подняли
  минимальный Node до 22. При обновлении Node в окружении можно поднять и
  их.
- Запущенный бэкенд (`market-analyzer serve`, порт 8080 по умолчанию) — без
  него `npm run dev` поднимется, но графики будут пустыми/ошибочными.

## Запуск

```bash
npm install
npm run dev          # http://localhost:5173
```

Бэкенд должен разрешать CORS с `http://localhost:5173` — это значение по
умолчанию у бэкендового `MA_API_CORS_ORIGIN` (см. корневой README), менять
не нужно для локальной разработки.

## Слой данных: Arrow, а не JSON (frontend-tz.md §2.2, FR-1.1/1.2)

`src/api/client.ts`'s `fetchRows` запрашивает `/ohlcv/*` и `/analytics/*`
с `Accept: application/vnd.apache.arrow.stream`. Если бэкенд отвечает
Arrow-потоком — `src/api/arrow.ts` разбирает его через `apache-arrow`,
читая колонки как типизированные значения напрямую, без
`JSON.parse`/промежуточных объектов. Если бэкенд не смог отдать Arrow
(`406`, либо `200` с другим `Content-Type`) — прозрачный fallback на JSON,
с предупреждением в консоль в dev-режиме.

Denominated-в-деньгах поля (цены, объёмы) идут по проводу как `Utf8`
(строки), не float — сервер обязан сохранять точность `DECIMAL(18,8)`.
`src/api/arrow.ts`/`src/api/endpoints.ts` парсят их в `number` уже на
границе, потому что дальше эти значения нужны только для отрисовки
графика (frontend-tz.md §2.3: пиксельная сетка грубее, чем 8 знаков после
запятой). Если/когда появится настоящая денежная арифметика на клиенте
(P&L, спреды) — это будет отдельный путь через `decimal.js-light` от
исходной строки, не от уже распарсенного `number`.

`GET /symbols` остаётся JSON-only — это маленький, редко обновляемый
реестр, Arrow там ничего не даёт.

### Пагинация: бэкенд режет любой ответ на 10 000 строк

`ma_api::state::ApiLimits.max_pagination_limit` (см. корневой репозиторий,
`crates/api/src/state.rs`) ограничивает один запрос 10 000 строками. На
`1m`-интервале это меньше 7 дней — 30-дневное окно с `limit` в одном
запросе **молча возвращало бы только самые старые ~7 дней и обрезало бы
всё недавнее** (`ASC ORDER BY` + `OFFSET 0`), а не "слишком много данных
за раз". `src/api/endpoints.ts`'s `fetchAllPages` поэтому всегда вычерпывает
все страницы (растёт `offset`, пока не придёт страница короче лимита) — ни
`fetchOhlcv`, ни аналитические запросы не принимают `limit`/`offset`
снаружи, чтобы этот класс бага не мог случайно вернуться в вызывающем коде.

## Живой поток: WS, реконнект, батчинг (frontend-tz.md §4.2, FR-2.x/3.3/7.x)

`src/stream/socket.ts` — голый `WebSocket` до `/stream/{symbol}?interval=`,
без Solid-зависимостей: реконнект с экспоненциальным бэкоффом (500мс, ×2,
потолок 15с, без ограничения попыток — FR-2.2), сброс бэкоффа на успешном
`open`. Разбирает реальный формат бэкенда (`ma_core::MarketEvent`'s
`#[serde(tag = "type")]`, frontend-tz.md BE-5) — `parseLiveMessage`
экспортирован и покрыт тестом на байтах, реально снятых с локального
бэкенда (`src/stream/socket.test.ts`).

`src/stream/buffer.ts` — rAF-батчинг (FR-2.3): при 1000 msg/сек (NFR-1.5)
это разница между 1000 обновлениями UI/сек и 60. При переполнении буфера
(>5000 необработанных, FR-2.4) оставляет только новейшие — деградирует
частоту, не отзывчивость.

`src/stream/useLiveStream.ts` — Solid-обвязка: одно WS-соединение на
текущие символ/интервал (пересоздаётся при их смене — FR-2.1), rAF-буферы
для сделок (тейп, капа в 500 — FR-2.4/7.2) и klines (живая свеча).
`document.visibilitychange` реально рвёт и переустанавливает соединение
(не просто игнорирует входящее) — на возврате видимости один REST
`refetch()` дальше делает свою работу, а не проигрывание накопленной
очереди (FR-2.5, буквальная формулировка ТЗ).

`PriceChart`'s `liveKline`-эффект (`src/charts/price-chart.tsx`) — отдельный
от исторического `data` → `setData()` пути; живой тик идёт через
`candleSeries.update()`/`volumeSeries.update()`. Проверено в реальном
браузере (профиль подтверждает: ни один живой тик не порождает новую
`price-chart:set-data` метку) — см. `tests/e2e/live-stream.spec.ts`.

## Тема, палитра для дальтоников, экспорт CSV (frontend-tz.md §8, Этап 5)

`state/theme.ts` держит два независимых, персистентных в `localStorage`
сигнала (FR-8.4): `theme` (`'dark' | 'light'`, DR-1: тёмная по умолчанию)
и `colorblindPalette` (булев, DR-4: меняет рост/падение на
сине-оранжевую пару). Переключаются из хедера (`ui/theme-toggle.tsx`).
Оба проецируются в атрибуты `data-theme`/`data-palette` на `<html>`, а
`tokens.css` переопределяет те же `--color-*` кастомные свойства под
каждую комбинацию — итого четыре палитры (тёмная/светлая ×
обычная/для дальтоников), собираются обычным CSS-каскадом.

**Запись атрибута в `state/theme.ts` — императивная, не `createEffect`.**
`PriceChart` и `IndicatorPanel` (ниже) тоже реагируют на те же сигналы
`theme`/`colorblindPalette`, перекрашивая уже созданные серии графика.
Если бы запись атрибута сама была ещё одним эффектом на том же сигнале,
порядок её выполнения относительно _их_ эффектов был бы не определён —
оба являются прямыми подписчиками одного сигнала, а не в отношении
родитель/потомок, так что какой из них Solid отработает первым — не
гарантировано. Запись атрибута прямо внутри той же функции, что меняет
сигнал, убирает гонку полностью: он гарантированно на месте до того, как
любой зависимый эффект где бы то ни было успеет отработать.

**Ни Lightweight Charts, ни uPlot не перекрашиваются сами при смене
палитры.** Обе библиотеки запекают резолвленные цвета-_строки_ в
график/серию в момент создания (`charts/theme.ts`'s `cssToken` — разовое
чтение `getComputedStyle`) — одна лишь смена `data-theme`/`data-palette`
не перекрашивает ничего. У `PriceChart` есть отдельный эффект
`on([theme, colorblindPalette], ..., { defer: true })`, который зовёт
`chart.applyOptions()`/`series.applyOptions()` со свежепрочитанными
цветами (и пересчитывает цвета столбиков объёма по каждому бару, и цвет
FR-5.3's маркера-подсветки, если он сейчас показан). У uPlot вообще нет
публичного API "перекрасить на лету", поэтому `IndicatorPanel` вместо
этого сравнивает `props.series[].color` и делает полный destroy+recreate
только когда цвет реально изменился — пересоздавать при каждом обычном
обновлении данных (рефетч запроса, живой тик) было бы неоправданно
дорого, так что важно именно сравнение, а не пересоздание само по себе.
`charts/theme.ts`'s `themedCssToken()` — то, что делает цвет-проп панели
(например, чтение `--color-accent` в `panels/ofi-panel.tsx`) реактивным
к палитре вообще — без этого цвет, переданный в `IndicatorPanel`,
обновлялся бы только когда `query.data` случайно менялся по совсем
другой причине.

**NFR-3.2 (контраст ≥ 4.5:1) породил два настоящих фикса, не только
новые палитры:**

- `--color-accent` (`#4f8cff` → `#2f6fed`) — белый текст на кнопках
  `bg-accent` (выбранный интервал в `IntervalSwitcher`, активная строка в
  `SymbolPicker`, "к новым сделкам" в `TradeTape`) давал 3.22:1 в
  _исходной, уже выпущенной_ тёмной теме. Это не баг только Этапа 5 —
  просто всплыл именно сейчас, при подборе акцента для светлой темы и
  решении оставить один оттенок на обе.
- Блендинг в `correlationColor()` (`panels/correlation-matrix.tsx`)
  ограничен 50%, не 100%. Текст `--color-fg` на чистом
  `--color-up`/`--color-down` фоне (корреляция ровно ±1, то есть каждая
  диагональная ячейка) проваливает контраст во всех четырёх палитрах —
  худший измеренный случай 1.56:1. 50% — максимальный блендинг, ещё
  проходящий 4.5:1 во всех четырёх; полное обоснование — в комментарии
  над `MAX_BLEND_PCT`.

**Экспорт CSV** (`export/csv.ts`): `buildOhlcvCsv` — чистый форматтер
(юнит-тестирован без DOM); `downloadCsv` делает часть с `Blob`/кликом по
ссылке. Достижим только через `import('./export/csv')` внутри
`app.tsx`'s `exportCsv`, по клику — NFR-2.6 явно называет "экспорт"
модулем, которого не должно быть в начальном бандле, и это подтверждено
в выводе сборки: `dist/assets/csv-*.js` — свой отдельный чанк ~0.3 КБ
gzip, не влит в вечный бандл.

**Честно о пробелах, а не молчание:** NFR-1.7 (часовой heap-тест),
NFR-3.4 (реальный кросс-браузерный прогон) и NFR-3.5 (компоновка < 1280px
— DR-7 сам фиксирует 1280px как минимальную рабочую ширину, а не точку
перехода на мобильную раскладку) не подтверждены буквально заявленным в
ТЗ методом в рамках этой сессии — по стоимости/времени (час реального
живого сеанса, реальные Safari/Firefox, реальный узкий вьюпорт) это
дороже, чем можно оправдать для разовой проверки. NFR-1.7 получило
компромиссный короткий прокси-тест (см. таблицу); NFR-3.4/3.5 — нет,
и это честнее, чем написать тест, который на самом деле не проверяет
то, что заявлено.

**Собственная находка NFR-1.2: первый прогон Lighthouse измерил не то.**
Самый первый `npm run lighthouse` на этом этапе легко прошёл (Performance
99-100) — но бэкенд не был поднят, и страница рендерила пустое
состояние/ошибку, а не настоящие свечи. LCP пустой страницы — не то, о
чём спрашивает NFR-1.2. Перезапуск бэкенда и повторный прогон дали
настоящие (всё ещё проходящие, 96-99) числа в таблице выше — напоминание,
что зелёный Lighthouse-скор что-то значит только если аудируемая страница
реально загрузила то, что измеряется.

**NFR-1.8 потребовал настоящего фикса, не просто теста.** У `main.tsx`'s
`QueryClient` не было дефолтного `staleTime` (у TanStack Query он `0` по
умолчанию), так что _каждый_ повторный визит на уже загруженный интервал
запускал фоновый рефетч, даже несмотря на то, что сам рендер приходил из
кэша мгновенно — формально это провал NFR-1.8's "без сетевого запроса",
не только духа требования. Исправлено глобальным `staleTime: 30_000` —
почему 30с и почему глобально, а не по каждому запросу — см. комментарий
в самом `main.tsx`.

**Настоящий зависший бэкенд, найденный случайно, не специально.** Запуск
`npm run lighthouse` (3 полных загрузки страницы) одновременно с
отдельным Playwright-скриптом, бьющим по тому же локальному
`market-analyzer serve`, заморозил бэкенд посреди запроса — TCP
подключился, запрос ушёл, ответа не было никогда (подтверждено свежим
`curl` спустя 7+ минут). Перезапуск процесса бэкенда сразу всё вылечил, и
дальше он оставался здоровым под повторными последовательными запросами.
Это забота бэкенда (вне рамок этого этапа — бэкенд был уже полностью
готов до начала Этапа 5), упомянуто здесь как настоящая находка из
тестирования в этой сессии, а не потому что что-то ниже это чинит: **не
гонять Lighthouse и отдельный browser-automation-скрипт по одному и тому
же локальному бэкенду одновременно.**

**Баг в самом наборе перф-тестов, найденный самостоятельно при добавлении
NFR-1.4/1.5.** `playwright.config.ts`'s проект `chromium-perf` унаследовал
верхнеуровневый `fullyParallel: true`. Пока в этом проекте был только
один тайминг-чувствительный тест (NFR-1.3), это не имело значения.
Добавление ещё четырёх в тот же файл на этом этапе сделало его значимым
немедленно: запуск всех 5 как параллельных worker-процессов сталкивает
их в конкуренцию за CPU _друг с другом_, и NFR-1.3 — не тронутый,
раньше стабильный — начал падать на 406мс против своего бюджета в 200мс
чисто из-за этой конкуренции. Исправлено установкой `fullyParallel: false`
именно для проекта `chromium-perf` (проект `chromium` не тронут и
по-прежнему полностью параллелен), так что тесты этого файла теперь идут
один за другим в одном worker'е.

**DuckDB-WASM: не реализован.** frontend-tz.md §8 явно помечает его
опциональным для Этапа 5 ("Опционально: DuckDB-WASM для локального
ресемплинга"), и ни одно функциональное требование (§4) от него не
зависит — весь ресемплинг/агрегация, нужные этому приложению, уже
происходят на сервере. Добавление WASM query-движка на клиенте ради нуля
обязательной функциональности было бы объёмом за пределами того, что
просит хоть один FR.

## Известное и важное для будущих этапов

- **`unwrap()` перед `.map()` по данным графика.** `props.data` у
  `PriceChart` в конечном счёте приходит из `@tanstack/solid-query`,
  чьи данные — Solid-стор (реактивный прокси). Профилирование показало:
  чтение 5-8 полей на 50 000+ строк через прокси стора съедает
  ~450 мс, при бюджете NFR-1.3 в 200 мс на весь первый рендер. Любой новый
  код, который делает объёмный проход по данным из
  `createQuery`/`createStore` вне JSX (не точечное реактивное чтение
  поля), должен явно звать `unwrap()` из `solid-js/store`.
- **Вторичные оверлеи — в `requestAnimationFrame`, не в критическом пути.**
  MA(20) добавляет свой собственный `LineSeries.setData()` — ещё один
  проход по всем барам вдобавок к свечам и объёму. Инлайново это добавляло
  ~50-70 мс к первому рендеру, чего хватало, чтобы 50k-свечной сценарий
  вылетал за 200-мсный бюджет NFR-1.3. `price-chart.tsx` считает и
  применяет MA одним кадром позже — то же правило будет нужно для любого
  следующего оверлея на основном графике.
- **Синхронизация зума (`charts/sync.ts`) публикует только настоящие
  жесты пользователя.** И Lightweight Charts, и uPlot зовут свой
  "видимый диапазон изменился" колбэк не только на реальном
  драге/зуме, но и на программном `setData()`/собственном
  автомасштабировании при монтировании. Если публиковать это в общий
  синхросигнал безусловно — какая панель домонтировалась/дозагрузилась
  последней, молча перетирает вид всем остальным (воспроизведено:
  автомасштаб только что смонтированной панели индикатора отменял
  `fitContent()` основного графика через мгновение после корректного
  рендера). `trackUserGestures` отслеживает реальные
  `pointerdown`/`pointermove`/`wheel` на элементе графика и пропускает
  публикацию, если рядом не было такого события — работает одинаково для
  обеих библиотек графиков.
- **uPlot не умеет зум колесом из коробки** — только драг-выделение
  (`cursor.drag.x`). Тестировать синхронизацию зума с панели нужно драгом,
  не `mouse.wheel`.
- **`/analytics/{symbol}/anomalies` не даёт непрерывный ряд z-score** —
  только строки, где z-score превышает `threshold`, и бэкенд отклоняет
  неположительный `threshold`. Панель "Volume Z-Score" поэтому рисует
  разрозненные маркеры (`style: 'points'`), а не выдуманную сплошную
  линию — это честное отражение того, что даёт эндпоинт, не баг.
- `SymbolPicker` (Этап 4) — полноценный combobox: клавиатурная навигация
  (`ArrowUp`/`ArrowDown`/`Enter`/`Escape`, ARIA
  `combobox`/`listbox`/`option`), недавно использованные символы первыми
  при пустом фильтре (`src/state/recent-symbols.ts`, `localStorage`, до 6
  штук), `data-hotkey-target="symbol-search"` для `/`-хоткея.
- DuckDB-WASM — не реализован, см. "NFR: результаты измерений" выше
  (Этап 5 явно помечает его опциональным, и ни один FR от него не зависит).
- **NFR-1.1: бюджет закрыт через прогрессивный `lazy()`, а не разовую
  чистку.** После Этапа 4 прод-сборка сначала ушла за бюджет (150.93 КБ
  gzip JS из 150 КБ) — ожидаемо, см. предыдущую версию этой заметки.
  Закрыто по одному компоненту за раз, с перемером после каждого:
  `CorrelationMatrix` → `AnomaliesTable` → `OfiPanel` → `TradeTape`, через
  `lazy(() => import(...))` + `<Suspense fallback={<PanelSkeleton />}>`
  (`src/ui/skeleton.tsx`) на месте использования; каждой цели нужен
  `export default` (`lazy()` только с ним и работает). Итог — 143.36 КБ
  из 150 КБ, с запасом, а не "еле прошло". Первые три — выключены по
  умолчанию (`OFI`/`Correlation` — чекбоксы, `Аномалии` — не дефолтная
  вкладка сайдбара) — очевидные кандидаты. `TradeTape` — тоньше: это
  **дефолтная** вкладка сайдбара, но у неё нет исторического REST-эндпоинта
  (только живой поток), так что она пустая независимо от скорости загрузки
  чанка — задержка на подгрузку чанка тут строго дешевле, чем ожидание
  первой сделки в любом случае. (Этап 5: тема/палитра/CSV-кнопка добавили
  ~4.5 КБ в вечный чанк — 147.85 КБ из 150, запас уже не такой, как был;
  следующему этапу почти наверняка снова понадобится либо новый `lazy()`,
  либо пересмотр того, что уже в вечном чанке.)
- **Баг в собственном `scripts/check-bundle-size.mjs`, всплывший ровно от
  появления `lazy()`.** До Этапа 4 скрипт суммировал gzip каждого `.js`/
  `.css` под `dist/assets/` — корректно, пока не было кодосплиттинга. После
  первого же `lazy()`-выноса (`CorrelationMatrix`) скрипт продолжал
  считать превышение бюджета, хотя вынесенный чанк специально не должен
  грузиться на первом экране (ровно то, что просит NFR-2.6). Причина —
  скрипт складывал вообще все файлы в `dist/assets/`, включая lazy-чанки,
  в "начальный" бюджет. Исправлено: скрипт теперь парсит сами `<script
src>`/`<link href>`-теги в `dist/index.html` (то, что браузер реально
  грузит eagerly на первом экране) и меряет gzip только этих файлов —
  lazy-чанк, ещё не запрошенный, в бюджет NFR-1.1 не входит по
  определению.
- **`createSeriesMarkers` (Lightweight Charts) рисует на тот же `<canvas>`,
  что и свечи — снаружи никакого запрашиваемого состояния нет.** Для
  FR-5.3 (клик по аномалии → прыжок графика к бару с маркером) e2e-тест не
  может проверить "прыжок применился" через DOM/API графика — там нечего
  читать. Решение — не мок внутреннего состояния и не пропуск теста, а
  один постоянный атрибут `data-last-jump-nonce` на корневом `div`
  `PriceChart` (`src/charts/price-chart.tsx`), который меняется в том же
  эффекте, что двигает `timeScale()` и зовёт `markers.setMarkers()`. Тест
  просто ждёт, что атрибут изменился — не заглядывает во внутренности
  графика.
- **Порог/окно у таблицы аномалий (FR-5.2) — дебounced через сигнал +
  `window.setTimeout`, не через сторонний хук.** Сырой сигнал инпута и
  "подтверждённый" сигнал (тот, что реально уходит в `queryKey`)
  разведены, синхронизация — в `createEffect`, который сбрасывает и
  переустанавливает таймер (300мс), с очисткой через `onCleanup`. Такой же
  паттерн — кандидат для любого следующего дебounced-контрола, отдельная
  библиотека под это не нужна.
- **Матрица корреляций красит ячейки через CSS `color-mix()`, поверх уже
  существующих DR-4 семантических токенов** (`--color-up`/`--color-down`/
  `--color-surface`), а не новой цветовой шкалой — диврегирующий градиент
  получается без единого нового токена. FR-6.3 (цвет не единственный
  носитель информации) — числовое значение корреляции лежит текстом в
  каждой ячейке независимо от цвета.
- **Тест на "хоткеи не должны срабатывать при вводе в поле" сам себя чуть
  не обманул.** Первая версия стартовала с интервала, который "стреляющий
  мимо guard'а" хоткей (`1` → `1m`) всё равно бы дал — то есть тест прошёл
  бы что при рабочей защите от тайпинга, что при полностью сломанной.
  Пойман до первого запуска, просто перечитыванием теста: старт на другом
  интервале (`15m`) делает поломку guard'а наблюдаемой (URL обратно
  скакнул бы на `1m`). Общий урок для будущих хоткей-тестов: стартовое
  состояние должно быть таким, чтобы баг и работающий код были
  различимы, а не просто "тест технически проверяет что-то".
- **`page.routeWebSocket` — не `page.route`.** Плейрайт мокает HTTP через
  `page.route`, но WS-соединения им не перехватываются вообще — нужен
  отдельный `page.routeWebSocket(pattern, ws => ...)` (см.
  `tests/e2e/live-stream.spec.ts`). Даёт `ws.send()`/`ws.close()` — этим
  снят по-настоящему реальный e2e для FR-2.2 (форс-обрыв → реконнект →
  данные без разрыва), не просто юнит-тест на бэкофф-таймер.
- **`npm run lighthouse` не находит Chrome сам по себе в этом окружении.**
  `@lhci/cli`'s healthcheck ищет системный `google-chrome`/`chromium`,
  которого тут нет — есть только тот, что уже скачал себе Playwright.
  Экспортировать `CHROME_PATH` перед запуском:
  `CHROME_PATH=$(node -e "console.log(require('playwright-core').chromium.executablePath())") npm run lighthouse`.
- **Не гонять `npm run lighthouse` параллельно с чем-то ещё, что бьёт по
  тому же локальному бэкенду.** См. "NFR: результаты измерений" выше —
  реальный зависший бэкенд, воспроизведённый именно так.

## Тесты

Юнит-тесты (`vitest`) лежат рядом с кодом (`src/**/*.test.ts`):
Arrow-парсинг проверен на побитово том же layout колонок, что и
`ma_api::arrow_ipc::ToRecordBatch` (`crates/api/src/arrow_ipc.rs`) —
`src/api/arrow.test.ts` гоняет реальный `apache-arrow` IPC round-trip, не
мок. `src/api/client.test.ts` покрывает fallback-логику (FR-1.2) и разбор
ошибок FR-5.2. `src/charts/indicators.test.ts` — клиентский MA(20).
`src/stream/socket.test.ts` разбирает WS-фреймы, реально снятые с
локального бэкенда (не выдуманные), включая точный формат BE-5.
`src/stream/buffer.test.ts` — rAF-батчинг и переполнение (FR-2.3/2.4).
`src/panels/stats.test.ts` — чистая функция подсчёта 24ч-изменения/объёма
для строки состояния (в т.ч. `null`, а не `0`, когда в окне нет баров или
текущая цена ещё не известна — эти два случая размечены разными полями,
не совпадением с нулём). `src/export/csv.test.ts` — CSV-форматтер, без
DOM (только `buildOhlcvCsv`, не `downloadCsv`). `src/panels/
correlation-matrix.test.ts` — `correlationColor()`'s 50%-cap (NFR-3.2,
см. выше).

E2E-файлы Playwright (`tests/e2e/*.spec.ts`) typecheck'аются отдельным
`tsconfig.e2e.json`, не общим `tsconfig.node.json` — `page.evaluate(() =>
...)`'s callback _source text_ здесь на самом деле выполняется в
браузере, который Playwright водит, а не в Node, и ему нужен `lib: DOM`
(`window`, `requestAnimationFrame`, `PerformanceObserver`'s `'longtask'`
entry type) — которого нет и не должно быть у остальных Node-контекстных
файлов (`vite.config.ts` и т.п.), делящих `tsconfig.node.json`.

E2E (`tests/e2e/`, Playwright) мокает `/symbols`, `/analytics/*` и
`/ohlcv/*` через `page.route` (WS — через `page.routeWebSocket`, см. выше)
— реальный бэкенд не нужен
(`tests/e2e/fixtures.ts` строит настоящие Arrow IPC байты того же формата,
что и бэкенд). Моки `/ohlcv/*` учитывают `limit`/`offset` и `to` так же,
как настоящий бэкенд — иначе FR-3.5 (догрузка истории) на маленьком
фикстурном наборе тут же ловит несогласованность порядка по времени (сам
FR-3.5 при этом отработал корректно; несогласованной была ровно
неосведомлённая о датах заглушка). `tests/e2e/analytics-panels.spec.ts`
(Этап 4) — клик по аномалии двигает график (FR-5.3, через
`data-last-jump-nonce`, см. выше), падение одного аналитического эндпоинта
не роняет остальные панели (FR-1.5, мок 500 на VWAP), хоткеи `1`-`6`/`/`/
`Esc` (FR-8.5) и то, что хоткеи не стреляют во время печати в поле поиска.
`perf.spec.ts` (NFR-1.3/1.4/1.5/1.7/1.8, Этап 5 добавил последние
четыре — см. "NFR: результаты измерений" выше) идёт отдельным
Playwright-проектом (`chromium-perf`) против прод-сборки (`vite build` +
`vite preview`), не против dev-сервера — тот же принцип, что у
NFR-1.2/Lighthouse CI. Этот проект специально не полностью параллелен
(`fullyParallel: false` в `playwright.config.ts`) — все пять тестов в
файле тайминг-чувствительны, и конкуренция за CPU между ними искажала
измерения (см. "NFR: результаты измерений" выше).

Первый запуск `npm run test:e2e` подтягивает браузер Chromium сам по себе
через Playwright; в песочнице без `sudo` `playwright install --with-deps`
не сработает — обычный `npx playwright install chromium` (без
`--with-deps`) собственных системных зависимостей не ставит и обычно
работает, если они уже есть в системе.
