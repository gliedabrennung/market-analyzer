# Market Analyzer — фронтенд

Дашборд для просмотра рыночных данных и аналитики поверх `market-analyzer`
(см. корневой `README.md`). ТЗ: `../frontend-tz.md`. Реализованы **Этап 1**,
**Этап 2** и **Этап 3** (§8): каркас, ценовой график, Arrow-транспорт, выбор
символа/интервала, URL как состояние, VWAP/MA(20) поверх графика, панели
индикаторов на uPlot (волатильность, OFI, z-score объёма), синхронизация
зума между всеми графиками, догрузка истории при скролле влево, живой
WebSocket-поток (реконнект с бэкоффом, батчинг через rAF, инкрементальное
обновление свечи через `update()`, виртуализированный тейп сделок).

## Требования

- Node.js — минимум как у Vite (`^20.19.0 || >=22.12.0`); проверено на
  20.20.2. `npm` в этой версии Node ругается баннером про неподдерживаемую
  версию — безвредно, это про сам `npm`, не про наш код.
- Тестовый тулчейн (`vitest`, `@testing-library/jest-dom`, `jsdom`) пока
  зафиксирован на последних мажорах, которые ещё **не** требуют Node 22+
  (`vitest@3`, `jest-dom@6`, `jsdom@25`) — их следующие мажоры уже подняли
  минимальный Node до 22. При обновлении Node в окружении можно поднять и
  их.
- Запущенный бэкенд (`market-analyzer serve`, порт 8080 по умолчанию) — без
  него `npm run dev` поднимется, но графики будут пустыми/ошибочными.

## Запуск

```bash
npm install
npm run dev          # http://localhost:5173
```

Бэкенд должен разрешать CORS с `http://localhost:5173` — это значение по
умолчанию у бэкендового `MA_API_CORS_ORIGIN` (см. корневой README), менять
не нужно для локальной разработки.

## Слой данных: Arrow, а не JSON (frontend-tz.md §2.2, FR-1.1/1.2)

`src/api/client.ts`'s `fetchRows` запрашивает `/ohlcv/*` и `/analytics/*`
с `Accept: application/vnd.apache.arrow.stream`. Если бэкенд отвечает
Arrow-потоком — `src/api/arrow.ts` разбирает его через `apache-arrow`,
читая колонки как типизированные значения напрямую, без
`JSON.parse`/промежуточных объектов. Если бэкенд не смог отдать Arrow
(`406`, либо `200` с другим `Content-Type`) — прозрачный fallback на JSON,
с предупреждением в консоль в dev-режиме.

Denominated-в-деньгах поля (цены, объёмы) идут по проводу как `Utf8`
(строки), не float — сервер обязан сохранять точность `DECIMAL(18,8)`.
`src/api/arrow.ts`/`src/api/endpoints.ts` парсят их в `number` уже на
границе, потому что дальше эти значения нужны только для отрисовки
графика (frontend-tz.md §2.3: пиксельная сетка грубее, чем 8 знаков после
запятой). Если/когда появится настоящая денежная арифметика на клиенте
(P&L, спреды) — это будет отдельный путь через `decimal.js-light` от
исходной строки, не от уже распарсенного `number`.

`GET /symbols` остаётся JSON-only — это маленький, редко обновляемый
реестр, Arrow там ничего не даёт.

### Пагинация: бэкенд режет любой ответ на 10 000 строк

`ma_api::state::ApiLimits.max_pagination_limit` (см. корневой репозиторий,
`crates/api/src/state.rs`) ограничивает один запрос 10 000 строками. На
`1m`-интервале это меньше 7 дней — 30-дневное окно с `limit` в одном
запросе **молча возвращало бы только самые старые ~7 дней и обрезало бы
всё недавнее** (`ASC ORDER BY` + `OFFSET 0`), а не "слишком много данных
за раз". `src/api/endpoints.ts`'s `fetchAllPages` поэтому всегда вычерпывает
все страницы (растёт `offset`, пока не придёт страница короче лимита) — ни
`fetchOhlcv`, ни аналитические запросы не принимают `limit`/`offset`
снаружи, чтобы этот класс бага не мог случайно вернуться в вызывающем коде.

## Живой поток: WS, реконнект, батчинг (frontend-tz.md §4.2, FR-2.x/3.3/7.x)

`src/stream/socket.ts` — голый `WebSocket` до `/stream/{symbol}?interval=`,
без Solid-зависимостей: реконнект с экспоненциальным бэкоффом (500мс, ×2,
потолок 15с, без ограничения попыток — FR-2.2), сброс бэкоффа на успешном
`open`. Разбирает реальный формат бэкенда (`ma_core::MarketEvent`'s
`#[serde(tag = "type")]`, frontend-tz.md BE-5) — `parseLiveMessage`
экспортирован и покрыт тестом на байтах, реально снятых с локального
бэкенда (`src/stream/socket.test.ts`).

`src/stream/buffer.ts` — rAF-батчинг (FR-2.3): при 1000 msg/сек (NFR-1.5)
это разница между 1000 обновлениями UI/сек и 60. При переполнении буфера
(>5000 необработанных, FR-2.4) оставляет только новейшие — деградирует
частоту, не отзывчивость.

`src/stream/useLiveStream.ts` — Solid-обвязка: одно WS-соединение на
текущие символ/интервал (пересоздаётся при их смене — FR-2.1), rAF-буферы
для сделок (тейп, капа в 500 — FR-2.4/7.2) и klines (живая свеча).
`document.visibilitychange` реально рвёт и переустанавливает соединение
(не просто игнорирует входящее) — на возврате видимости один REST
`refetch()` дальше делает свою работу, а не проигрывание накопленной
очереди (FR-2.5, буквальная формулировка ТЗ).

`PriceChart`'s `liveKline`-эффект (`src/charts/price-chart.tsx`) — отдельный
от исторического `data` → `setData()` пути; живой тик идёт через
`candleSeries.update()`/`volumeSeries.update()`. Проверено в реальном
браузере (профиль подтверждает: ни один живой тик не порождает новую
`price-chart:set-data` метку) — см. `tests/e2e/live-stream.spec.ts`.

## Известное и важное для будущих этапов

- **`unwrap()` перед `.map()` по данным графика.** `props.data` у
  `PriceChart` в конечном счёте приходит из `@tanstack/solid-query`,
  чьи данные — Solid-стор (реактивный прокси). Профилирование показало:
  чтение 5-8 полей на 50 000+ строк через прокси стора съедает
  ~450 мс, при бюджете NFR-1.3 в 200 мс на весь первый рендер. Любой новый
  код, который делает объёмный проход по данным из
  `createQuery`/`createStore` вне JSX (не точечное реактивное чтение
  поля), должен явно звать `unwrap()` из `solid-js/store`.
- **Вторичные оверлеи — в `requestAnimationFrame`, не в критическом пути.**
  MA(20) добавляет свой собственный `LineSeries.setData()` — ещё один
  проход по всем барам вдобавок к свечам и объёму. Инлайново это добавляло
  ~50-70 мс к первому рендеру, чего хватало, чтобы 50k-свечной сценарий
  вылетал за 200-мсный бюджет NFR-1.3. `price-chart.tsx` считает и
  применяет MA одним кадром позже — то же правило будет нужно для любого
  следующего оверлея на основном графике.
- **Синхронизация зума (`charts/sync.ts`) публикует только настоящие
  жесты пользователя.** И Lightweight Charts, и uPlot зовут свой
  "видимый диапазон изменился" колбэк не только на реальном
  драге/зуме, но и на программном `setData()`/собственном
  автомасштабировании при монтировании. Если публиковать это в общий
  синхросигнал безусловно — какая панель домонтировалась/дозагрузилась
  последней, молча перетирает вид всем остальным (воспроизведено:
  автомасштаб только что смонтированной панели индикатора отменял
  `fitContent()` основного графика через мгновение после корректного
  рендера). `trackUserGestures` отслеживает реальные
  `pointerdown`/`pointermove`/`wheel` на элементе графика и пропускает
  публикацию, если рядом не было такого события — работает одинаково для
  обеих библиотек графиков.
- **uPlot не умеет зум колесом из коробки** — только драг-выделение
  (`cursor.drag.x`). Тестировать синхронизацию зума с панели нужно драгом,
  не `mouse.wheel`.
- **`/analytics/{symbol}/anomalies` не даёт непрерывный ряд z-score** —
  только строки, где z-score превышает `threshold`, и бэкенд отклоняет
  неположительный `threshold`. Панель "Volume Z-Score" поэтому рисует
  разрозненные маркеры (`style: 'points'`), а не выдуманную сплошную
  линию — это честное отражение того, что даёт эндпоинт, не баг.
- `SymbolPicker` — минимальный фильтрующий инпут, не полноценный combobox
  с клавиатурной навигацией (это FR-8.1 в объёме Этапа 4, где вообще
  проверяется полный проход по интерфейсу с клавиатуры, NFR-3.1).
- Панели аномалий/корреляций (Этап 4), светлая тема и DuckDB-WASM (Этап 5)
  — не реализованы, это следующие этапы `frontend-tz.md`.
- **NFR-1.1 запас практически исчерпан.** Прод-сборка — ~149.8 КБ gzip JS
  из бюджета 150 КБ (`npm run build:check-size` — обёртка над
  `scripts/check-bundle-size.mjs`, реальный gzip каждого файла в `dist/`,
  не оценка `rollup-plugin-visualizer`, которая тут же настроена
  (`dist/stats.html` после сборки) и даёт разбивку по пакетам). По ней
  `apache-arrow` — определённо самый тяжёлый пакет в бандле (~48 КБ gzip
  реального веса, больше чем `lightweight-charts` и `uplot` вместе с
  большим отрывом; в §2.1 ТЗ размер не указан, в отличие от остальных
  библиотек стека) — это плата за парсинг Arrow IPC произвольной схемы,
  а не что-то, что легко подрезать точечным импортом (`sideEffects: false`
  уже объявлен в его `package.json`, тришейкинг и так работает). Этапу 4
  (таблица аномалий, матрица корреляций) почти наверняка понадобится
  вынести хотя бы одну новую панель за `lazy()`/динамический `import()`
  (NFR-2.6's принцип, не только для DuckDB-WASM) — бюджета на "добавить
  ещё один синхронный импорт" уже не осталось.
- **`page.routeWebSocket` — не `page.route`.** Плейрайт мокает HTTP через
  `page.route`, но WS-соединения им не перехватываются вообще — нужен
  отдельный `page.routeWebSocket(pattern, ws => ...)` (см.
  `tests/e2e/live-stream.spec.ts`). Даёт `ws.send()`/`ws.close()` — этим
  снят по-настоящему реальный e2e для FR-2.2 (форс-обрыв → реконнект →
  данные без разрыва), не просто юнит-тест на бэкофф-таймер.

## Тесты

Юнит-тесты (`vitest`) лежат рядом с кодом (`src/**/*.test.ts`):
Arrow-парсинг проверен на побитово том же layout колонок, что и
`ma_api::arrow_ipc::ToRecordBatch` (`crates/api/src/arrow_ipc.rs`) —
`src/api/arrow.test.ts` гоняет реальный `apache-arrow` IPC round-trip, не
мок. `src/api/client.test.ts` покрывает fallback-логику (FR-1.2) и разбор
ошибок FR-5.2. `src/charts/indicators.test.ts` — клиентский MA(20).
`src/stream/socket.test.ts` разбирает WS-фреймы, реально снятые с
локального бэкенда (не выдуманные), включая точный формат BE-5.
`src/stream/buffer.test.ts` — rAF-батчинг и переполнение (FR-2.3/2.4).

E2E (`tests/e2e/`, Playwright) мокает `/symbols`, `/analytics/*` и
`/ohlcv/*` через `page.route` (WS — через `page.routeWebSocket`, см. выше)
— реальный бэкенд не нужен
(`tests/e2e/fixtures.ts` строит настоящие Arrow IPC байты того же формата,
что и бэкенд). Моки `/ohlcv/*` учитывают `limit`/`offset` и `to` так же,
как настоящий бэкенд — иначе FR-3.5 (догрузка истории) на маленьком
фикстурном наборе тут же ловит несогласованность порядка по времени (сам
FR-3.5 при этом отработал корректно; несогласованной была ровно
неосведомлённая о датах заглушка). `perf.spec.ts` (NFR-1.3) идёт отдельным
Playwright-проектом против прод-сборки (`vite build` + `vite preview`), не
против dev-сервера — тот же принцип, что у NFR-1.2/Lighthouse CI.

Первый запуск `npm run test:e2e` подтягивает браузер Chromium сам по себе
через Playwright; в песочнице без `sudo` `playwright install --with-deps`
не сработает — обычный `npx playwright install chromium` (без
`--with-deps`) собственных системных зависимостей не ставит и обычно
работает, если они уже есть в системе.
