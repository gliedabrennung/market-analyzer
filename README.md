# Market Analyzer

Сервис сбора и аналитики биржевых данных на Rust + DuckDB, с веб-дашбордом
на SolidJS. Бэкенд собирает OHLCV-свечи и сделки с Binance (REST backfill +
WebSocket live-поток), хранит их в партиционированном Parquet, считает
аналитику (VWAP, волатильность, аномалии объёма, OFI, корреляции,
межбиржевой спред) через DuckDB SQL и отдаёт всё через CLI и HTTP API.
Фронтенд — дашборд поверх этого API: ценовой график со свечами и объёмом,
индикаторы (VWAP, MA(20), волатильность, OFI, z-score объёма аномалий) на
синхронизированных по зуму панелях, живой WebSocket-поток с реконнектом и
виртуализированным тейпом сделок, таблица аномалий с переходом к бару на
графике, матрица корреляций, тёмная/светлая тема с палитрой для
дальтоников и экспорт данных в CSV.

## Требования

### Бэкенд

- Rust ≥ 1.80 (см. `rust-toolchain`/`rust-version` в `Cargo.toml`)
- Linux или macOS
- Компилятор C++ (для сборки DuckDB из исходников, `features = ["bundled"]`) —
  на большинстве систем уже стоит; первая сборка компилирует DuckDB с нуля и
  занимает **10-20 минут**, дальше пересборки быстрые (инкрементальные)
- Никаких внешних сервисов не требуется — только файловая система

### Фронтенд

- Node.js — минимум как у Vite (`^20.19.0 || >=22.12.0`); проверено на
  20.20.2. `npm` в этой версии Node ругается баннером про неподдерживаемую
  версию — безвредно, это про сам `npm`, не про наш код.
- Тестовый тулчейн (`vitest`, `@testing-library/jest-dom`, `jsdom`) пока
  зафиксирован на последних мажорах, которые ещё **не** требуют Node 22+
  (`vitest@3`, `jest-dom@6`, `jsdom@25`) — их следующие мажоры уже подняли
  минимальный Node до 22. При обновлении Node в окружении можно поднять и
  их.
- Запущенный бэкенд (`market-analyzer serve`, порт 8080 по умолчанию) — без
  него `npm run dev` поднимется, но графики будут пустыми/ошибочными.

## Запуск

### Docker — весь стек одной командой

```bash
docker compose up --build
```

Поднимает оба сервиса: бэкенд (`market-analyzer serve`, порт 8080) и
фронтенд (прод-сборка `vite build`, отданная nginx'ом, порт 8081).
Данные — в `./data/` на хосте, пробрасываются volume'ом в бэкенд-контейнер
(тот же каталог, что и без Docker) — ничего не теряется между
`docker compose down`/`up`.

При первом запуске на пустом `./data/` бэкенд-контейнер сам разово
выполняет `symbols --refresh` (нужна сеть до Binance) —
`docker/backend-entrypoint.sh`, та же необходимость, что описана у
команды `serve` ниже, просто закрытая автоматически. Историческую
загрузку сам не делает — это отдельное действие, специфичное для
конкретных символов/диапазона. `backend`-сервис держит `meta.duckdb`
открытой на чтение постоянно (пока крутится `serve`), а DuckDB допускает
только одного писателя на файл разом — перед любой пишущей командой
сервис нужно сперва остановить:

```bash
docker compose stop backend
docker compose run --rm backend backfill \
  --symbol BTCUSDT --interval 1m --from 2026-08-01 --to 2026-08-31
docker compose start backend
```

Так же — через `docker compose run --rm backend <команда>` (не
`market-analyzer <команда>`: `ENTRYPOINT` уже подставляет бинарь сам,
повторное имя команды будет воспринято как неизвестная подкоманда) —
доступна любая другая CLI-команда (`query`, `compact`, `symbols` без
`--refresh`, ...) без отдельного локального `cargo build`.

До первого `backfill` для символа данных ещё нет, и вьюхи `klines`/
`trades` в DuckDB ещё не созданы — `/ohlcv` и `/analytics/*` до этого
момента отвечают `500 internal_error` (подробности — в логе `serve`, не
в теле ответа). Это ожидаемо и не специфично для Docker. Сразу после
первого же успешного `backfill` данные видны без каких-либо
дополнительных действий: пишущие команды сами публикуют вьюхи поверх
только что записанных файлов.

Не переиспользуйте нативный (не-Docker) `./data/` при переходе на
Docker: `meta.duckdb` хранит вьюхи с абсолютным путём к parquet-файлам,
зафиксированным на момент их создания, — путь с хоста
(`/home/.../service/data/...`) не существует внутри контейнера с
volume-маунтом `/data`, и запросы упадут с `No files found that match
the pattern ...`. Начинайте с пустого `./data/` под Docker или удалите
`meta.duckdb` и пересоздайте вьюхи (`symbols --refresh` /
`backfill`) уже изнутри контейнера.

Порты переопределяются переменными окружения (`.env` рядом с
`docker-compose.yml` или экспортом перед командой) — `MA_API_CORS_ORIGIN`
у бэкенда подстраивается под `FRONTEND_PORT` автоматически:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `BACKEND_PORT` | `8080` | порт бэкенда на хосте |
| `FRONTEND_PORT` | `8081` | порт фронтенда на хосте |

**`VITE_API_BASE_URL` у фронтенда запекается в JS-бандл на этапе сборки**
(Vite, см. "Конфигурация" ниже), не читается в рантайме — смена
`BACKEND_PORT` требует `docker compose build frontend` заново, простого
`docker compose up` после смены переменной недостаточно.

Первая сборка бэкенда компилирует DuckDB с нуля (10-20 минут — см.
"Требования" выше); `Dockerfile` использует `cargo-chef`, так что
последующие пересборки после правки только исходников (не
`Cargo.toml`/`Cargo.lock`) — быстрые, зависимости пересобираться не
должны.

```bash
docker compose logs -f backend    # логи
docker compose ps                 # статус/health обоих сервисов
docker compose down                # остановить (данные в ./data остаются)
```

### Нативно, пошагово

Соберите бэкенд (см. "Сборка и скрипты" выше) — дальше в примерах
`market-analyzer` подразумевает `target/release/market-analyzer` (либо
добавьте `target/release` в `PATH`, либо вызывайте по полному пути).

```bash
# 1. Реестр символов — нужен для API-валидации и справки; выполнить один
#    раз перед первым использованием HTTP API
market-analyzer symbols --refresh

# 2. Историческая загрузка
market-analyzer backfill --symbol BTCUSDT --interval 1m \
  --from 2026-08-01 --to 2026-08-31

# 3. Аналитика прямо из CLI
market-analyzer query --name vwap --symbol BTCUSDT \
  --param interval=1m --param window=20 --format table

# 4. Live-поток в реальном времени, Ctrl+C — грациозная остановка
market-analyzer stream --symbol BTCUSDT --symbol ETHUSDT --dataset trades

# 5. HTTP API
market-analyzer serve --port 8080
curl 'http://localhost:8080/ohlcv/BTCUSDT?interval=1m&from=2026-08-01&to=2026-08-02'

# 6. Склейка part-файлов партиции (по мере накопления данных, не обязательна
#    перед первым запуском)
market-analyzer compact --symbol BTCUSDT
```

Данные по умолчанию лежат в `./data/` (`data/klines/`, `data/trades/`,
`data/meta.duckdb`).

Дальше — фронтенд, отдельным терминалом (бэкенд из шага 5 должен уже
крутиться):

```bash
cd frontend
npm install
npm run dev          # http://localhost:5173
```

Бэкенд должен разрешать CORS с `http://localhost:5173` — это значение по
умолчанию у бэкендового `MA_API_CORS_ORIGIN` (см. "Конфигурация" ниже),
менять не нужно для локальной разработки.

Для прод-сборки фронтенда без Docker: `npm run build` кладёт статику в
`frontend/dist/` — раздать её можно любым статическим сервером
(`npm run preview` — для локальной проверки, порт 4173); не забудьте
`VITE_API_BASE_URL` на этапе сборки, если бэкенд не на
`http://localhost:8080` (см. "Конфигурация" ниже).

## Конфигурация

### Бэкенд

Настройки берутся из значений по умолчанию → TOML-файла (`--config path.toml`)
→ переменных окружения с префиксом `MA_` (наивысший приоритет).

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `MA_DATA_DIR` | `data` | корень Parquet-данных |
| `MA_META_DB_PATH` | `data/meta.duckdb` | путь к метабазе |
| `MA_BINANCE_BASE_URL` | `https://api.binance.com` | REST-эндпоинт биржи |
| `MA_REQUESTS_PER_SECOND` | `5` | лимит собственного rate limiter'а |
| `MA_API_MAX_DATE_RANGE_DAYS` | `366` | максимальная ширина `from`/`to` в API |
| `MA_API_DB_POOL_SIZE` | `4` | число read-only DuckDB-подключений у `serve` |
| `MA_API_CORS_ORIGIN` | `http://localhost:5173` | разрешённый origin фронтенда: и `Access-Control-Allow-Origin` для HTTP, и проверка `Origin` у `WS /stream/{symbol}` |
| `MA_API_MAX_WS_CONNECTIONS` | `64` | потолок одновременных клиентов `WS /stream/{symbol}` |

`--config`/`MA_DATA_DIR` и т.п. должны указывать на один и тот же каталог во
всех командах одного проекта — иначе `backfill`/`stream` и `query`/`serve`
будут смотреть на разные данные.

### Фронтенд

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `VITE_API_BASE_URL` | `http://localhost:8080` | адрес `market-analyzer serve` |

Читается Vite'ом на этапе **сборки** (`import.meta.env`), не в рантайме —
для прод-сборки (`npm run build`, и в частности `frontend/Dockerfile`)
значение запекается в JS-бандл раз и навсегда. Смена адреса бэкенда после
сборки требует пересборки, не просто перезапуска раздающего сервера.

## Команды CLI

### `backfill`
```
market-analyzer backfill --symbol SYM [--symbol SYM ...] --interval {1m,5m,15m,1h,4h,1d} --from YYYY-MM-DD [--to YYYY-MM-DD]
```
Пагинация и обработка rate-limit (429 — бэкофф, 418 — пауза по
`Retry-After`) — внутри, автоматически. Идемпотентно: повторный запуск не
плодит дубли (дедуп по `(exchange, symbol, interval, open_time)`).

### `stream`
```
market-analyzer stream --symbol SYM [--symbol SYM ...] [--dataset klines|trades]
```
Klines стримятся на `1m`. Живёт, пока не придёт `SIGINT`/`SIGTERM` —
флашит буфер и завершается за секунды. При обрыве соединения — реконнект
с бэкоффом и обязательный REST-добор пропущенного окна.

### `query`
```
market-analyzer query --name NAME --symbol SYM [--param k=v ...] [--format table|json|csv]
```
`NAME` — один из: `resample`, `vwap`, `volatility`, `anomalies`, `ofi`,
`correlation`, `spread`. Параметры (все опциональны, есть разумные
дефолты) — через `--param`:

| `--name` | Параметры |
|---|---|
| `vwap` | `interval` (1m), `window` (20) |
| `volatility` | `interval` (1m), `window` (20) |
| `anomalies` | `interval` (1m), `window` (100), `threshold` (3.0) |
| `resample` | `bucket_seconds` (300), `from`, `to` |
| `ofi` | `bucket_seconds` (60), `from`, `to` |
| `correlation` | `symbols=A,B,C` (нужно ≥2), `interval` (1m) |
| `spread` | `interval` (1m), `other_symbol` (обязателен), `exchange`/`other_exchange` (binance) |

### `symbols`
```
market-analyzer symbols [--refresh]
```
Без `--refresh` — печатает текущий реестр; с `--refresh` — синхронизирует
его с `exchangeInfo` биржи (нужно один раз перед первым использованием API).

### `compact`
```
market-analyzer compact [--symbol SYM] [--date YYYY-MM-DD]
```
Сливает `part-*.parquet` каждой затронутой партиции в один файл. Без
флагов — проходит по всем партициям обоих датасетов. Безопасно к падению:
новый файл дописывается и **проверяется агрегатной чек-суммой** против
оригиналов до того, как оригиналы удаляются.

### `serve`
```
market-analyzer serve [--port 8080]
```
Поднимает HTTP API (см. ниже). Требует, чтобы `symbols --refresh` уже был
хоть раз запущен — иначе `/ohlcv`, `/analytics/*` и `/stream/*` будут
всегда отвечать `404 unknown_symbol`.

## HTTP API

| Метод | Путь | Параметры |
|---|---|---|
| GET | `/health` | — |
| GET | `/symbols` | — |
| GET | `/ohlcv/{symbol}` | `interval`, `from`, `to`, `limit`, `offset` |
| GET | `/analytics/{symbol}/vwap` | `interval`, `window`, `limit`, `offset` |
| GET | `/analytics/{symbol}/volatility` | `interval`, `window`, `limit`, `offset` |
| GET | `/analytics/{symbol}/anomalies` | `interval`, `window`, `threshold`, `limit`, `offset` |
| GET | `/analytics/{symbol}/ofi` | `bucket`, `from`, `to`, `limit`, `offset` |
| GET | `/analytics/correlation` | `symbols` (через запятую, максимум 10 — расчёт O(n²)), `interval` |
| WS | `/stream/{symbol}` | `interval` (по умолчанию `1m`) — проброс живых сделок и klines |
| GET | `/metrics` | Prometheus-метрики |

`/ohlcv/*` и `/analytics/*` отдают Apache Arrow IPC stream при
`Accept: application/vnd.apache.arrow.stream`; без этого заголовка —
обычный JSON. Decimal-поля (цены, объёмы) в Arrow-колонках — `Utf8`, не
float: точность не теряется при сериализации.

`WS /stream/{symbol}` шлёт JSON с полем `type` (`trade` / `kline` /
`heartbeat`, не реже раза в 20 с) — `ma_core::MarketEvent` сериализуется с
`#[serde(tag = "type")]`; подписка идёт сразу на `Trade` и
`Kline(interval)`.

`from`/`to` — `YYYY-MM-DD` или RFC3339. Ошибки — всегда
`{"error":{"code","message","details"}}`: `400` — невалидные параметры,
`404` — неизвестный символ, `429` — превышен лимит, `500` — внутренняя
ошибка. `429` сейчас отдаётся в одном случае: когда занят весь бюджет
одновременных WS-клиентов (`MA_API_MAX_WS_CONNECTIONS`); пер-запросного
rate limiting на HTTP-уровне нет.

Браузерные CORS-правила не распространяются на WebSocket-рукопожатие,
поэтому `WS /stream/{symbol}` сам сверяет заголовок `Origin` с
`MA_API_CORS_ORIGIN` и отвечает `400` на чужой origin. Запросы вообще без
`Origin` (curl, серверные клиенты, сам CLI) проверку проходят — этот
заголовок ставит браузер, и его отсутствие означает, что за запросом не
стоит страница.

Тело `500` всегда содержит ровно `"internal error"` без подробностей:
исходный текст ошибки (абсолютные пути каталога данных, упавший SQL)
пишется в лог сервера, а не отдаётся вызывающему.

```bash
curl 'http://localhost:8080/analytics/BTCUSDT/vwap?window=20&limit=5'
curl 'http://localhost:8080/analytics/correlation?symbols=BTCUSDT,ETHUSDT'
```

## Фронтенд: архитектура и детали реализации

### Слой данных: Arrow, а не JSON

`src/api/client.ts`'s `fetchRows` запрашивает `/ohlcv/*` и `/analytics/*`
с `Accept: application/vnd.apache.arrow.stream`. Если бэкенд отвечает
Arrow-потоком — `src/api/arrow.ts` разбирает его через `apache-arrow`,
читая колонки как типизированные значения напрямую, без
`JSON.parse`/промежуточных объектов. Если бэкенд не смог отдать Arrow
(`406`, либо `200` с другим `Content-Type`) — прозрачный fallback на JSON,
с предупреждением в консоль в dev-режиме.

Денежные поля (цены, объёмы) идут по проводу как `Utf8` (строки), не
float — сервер обязан сохранять точность `DECIMAL(18,8)`.
`src/api/arrow.ts`/`src/api/endpoints.ts` парсят их в `number` уже на
границе, потому что дальше эти значения нужны только для отрисовки
графика (пиксельная сетка всё равно грубее, чем 8 знаков после запятой).
Если/когда появится настоящая денежная арифметика на клиенте (P&L,
спреды) — это будет отдельный путь через `decimal.js-light` от исходной
строки, не от уже распарсенного `number`.

`GET /symbols` остаётся JSON-only — это маленький, редко обновляемый
реестр, Arrow там ничего не даёт.

#### Пагинация: бэкенд режет любой ответ на 10 000 строк

`ma_api::state::ApiLimits.max_pagination_limit` (см. `crates/api/src/state.rs`)
ограничивает один запрос 10 000 строками. На `1m`-интервале это меньше 7
дней — 30-дневное окно с `limit` в одном запросе **молча возвращало бы
только самые старые ~7 дней и обрезало бы всё недавнее** (`ASC ORDER BY`
+ `OFFSET 0`), а не "слишком много данных за раз". `src/api/endpoints.ts`'s
`fetchAllPages` поэтому всегда вычерпывает все страницы (растёт `offset`,
пока не придёт страница короче лимита) — ни `fetchOhlcv`, ни
аналитические запросы не принимают `limit`/`offset` снаружи, чтобы этот
класс бага не мог случайно вернуться в вызывающем коде.

### Живой поток: WS, реконнект, батчинг

`src/stream/socket.ts` — голый `WebSocket` до `/stream/{symbol}?interval=`,
без Solid-зависимостей: реконнект с экспоненциальным бэкоффом (500мс, ×2,
потолок 15с, без ограничения попыток), сброс бэкоффа на успешном `open`.
Разбирает реальный формат бэкенда (`ma_core::MarketEvent`'s
`#[serde(tag = "type")]`) — `parseLiveMessage` экспортирован и покрыт
тестом на байтах, реально снятых с локального бэкенда
(`src/stream/socket.test.ts`).

`src/stream/buffer.ts` — rAF-батчинг: при 1000 сообщений/сек это разница
между 1000 обновлениями UI/сек и 60. При переполнении буфера (>5000
необработанных) оставляет только новейшие — деградирует частоту, не
отзывчивость.

`src/stream/useLiveStream.ts` — Solid-обвязка: одно WS-соединение на
текущие символ/интервал (пересоздаётся при их смене), rAF-буферы для
сделок (тейп, капа в 500) и klines (живая свеча).
`document.visibilitychange` реально рвёт и переустанавливает соединение
(не просто игнорирует входящее) — на возврате видимости один REST
`refetch()` дальше делает свою работу, а не проигрывание накопленной
очереди.

`PriceChart`'s `liveKline`-эффект (`src/charts/price-chart.tsx`) — отдельный
от исторического `data` → `setData()` пути; живой тик идёт через
`candleSeries.update()`/`volumeSeries.update()`. Проверено в реальном
браузере (профиль подтверждает: ни один живой тик не порождает новую
`price-chart:set-data` метку) — см. `tests/e2e/live-stream.spec.ts`.

### Тема, палитра для дальтоников, экспорт CSV

`state/theme.ts` держит два независимых, персистентных в `localStorage`
сигнала: `theme` (`'dark' | 'light'`, тёмная по умолчанию) и
`colorblindPalette` (булев — меняет цвета роста/падения на
сине-оранжевую пару). Переключаются из хедера (`ui/theme-toggle.tsx`).
Оба проецируются в атрибуты `data-theme`/`data-palette` на `<html>`, а
`tokens.css` переопределяет те же `--color-*` кастомные свойства под
каждую комбинацию — итого четыре палитры (тёмная/светлая ×
обычная/для дальтоников), собираются обычным CSS-каскадом.

**Запись атрибута в `state/theme.ts` — императивная, не `createEffect`.**
`PriceChart` и `IndicatorPanel` (ниже) тоже реагируют на те же сигналы
`theme`/`colorblindPalette`, перекрашивая уже созданные серии графика.
Если бы запись атрибута сама была ещё одним эффектом на том же сигнале,
порядок её выполнения относительно _их_ эффектов был бы не определён —
оба являются прямыми подписчиками одного сигнала, а не в отношении
родитель/потомок, так что какой из них Solid отработает первым — не
гарантировано. Запись атрибута прямо внутри той же функции, что меняет
сигнал, убирает гонку полностью: он гарантированно на месте до того, как
любой зависимый эффект где бы то ни было успеет отработать.

**Ни Lightweight Charts, ни uPlot не перекрашиваются сами при смене
палитры.** Обе библиотеки запекают резолвленные цвета-_строки_ в
график/серию в момент создания (`charts/theme.ts`'s `cssToken` — разовое
чтение `getComputedStyle`) — одна лишь смена `data-theme`/`data-palette`
не перекрашивает ничего. У `PriceChart` есть отдельный эффект
`on([theme, colorblindPalette], ..., { defer: true })`, который зовёт
`chart.applyOptions()`/`series.applyOptions()` со свежепрочитанными
цветами (и пересчитывает цвета столбиков объёма по каждому бару, и цвет
маркера-подсветки клика по аномалии, если он сейчас показан). У uPlot
вообще нет публичного API "перекрасить на лету", поэтому `IndicatorPanel`
вместо этого сравнивает `props.series[].color` и делает полный
destroy+recreate только когда цвет реально изменился — пересоздавать при
каждом обычном обновлении данных (рефетч запроса, живой тик) было бы
неоправданно дорого, так что важно именно сравнение, а не пересоздание
само по себе. `charts/theme.ts`'s `themedCssToken()` — то, что делает
цвет-проп панели (например, чтение `--color-accent` в
`panels/ofi-panel.tsx`) реактивным к палитре вообще — без этого цвет,
переданный в `IndicatorPanel`, обновлялся бы только когда `query.data`
случайно менялся по совсем другой причине.

**Требование контраста ≥ 4.5:1 породило два настоящих фикса, не только
новые палитры:**

- `--color-accent` (`#4f8cff` → `#2f6fed`) — белый текст на кнопках
  `bg-accent` (выбранный интервал в `IntervalSwitcher`, активная строка в
  `SymbolPicker`, "к новым сделкам" в `TradeTape`) давал 3.22:1 в
  _исходной, уже выпущенной_ тёмной теме. Это не баг только текущей
  правки — просто всплыл именно сейчас, при подборе акцента для светлой
  темы и решении оставить один оттенок на обе.
- Блендинг в `correlationColor()` (`panels/correlation-matrix.tsx`)
  ограничен 50%, не 100%. Текст `--color-fg` на чистом
  `--color-up`/`--color-down` фоне (корреляция ровно ±1, то есть каждая
  диагональная ячейка) проваливает контраст во всех четырёх палитрах —
  худший измеренный случай 1.56:1. 50% — максимальный блендинг, ещё
  проходящий 4.5:1 во всех четырёх; полное обоснование — в комментарии
  над `MAX_BLEND_PCT`.

**Экспорт CSV** (`export/csv.ts`): `buildOhlcvCsv` — чистый форматтер
(юнит-тестирован без DOM); `downloadCsv` делает часть с `Blob`/кликом по
ссылке. Достижим только через `import('./export/csv')` внутри
`app.tsx`'s `exportCsv`, по клику — экспорт не должен быть в начальном
JS-бандле, и это подтверждено в выводе сборки: `dist/assets/csv-*.js` —
свой отдельный чанк ~0.3 КБ gzip, не влит в вечный бандл.

**Честно о пробелах, а не молчание:** часовой heap-тест, реальный
кросс-браузерный прогон и раскладка < 1280px не подтверждены заявленным
методом измерения в рамках этой работы — по стоимости/времени (час
реального живого сеанса, реальные Safari/Firefox, реальный узкий
вьюпорт) это дороже, чем можно оправдать для разовой проверки. Рост heap
получил компромиссный короткий прокси-тест (см. таблицу);
кросс-браузерность и узкий вьюпорт — нет, и это честнее, чем написать
тест, который на самом деле не проверяет то, что заявлено.

**Собственная находка: первый прогон Lighthouse измерил не то.** Самый
первый `npm run lighthouse` легко прошёл (Performance 99-100) — но
бэкенд не был поднят, и страница рендерила пустое состояние/ошибку, а не
настоящие свечи. LCP пустой страницы — не то, что нужно было измерить.
Перезапуск бэкенда и повторный прогон дали настоящие (всё ещё
проходящие, 96-99) числа в таблице выше — напоминание, что зелёный
Lighthouse-скор что-то значит только если аудируемая страница реально
загрузила то, что измеряется.

**"Смена на закэшированный интервал — без сетевого запроса" потребовала
настоящего фикса, не просто теста.** У `main.tsx`'s `QueryClient` не
было дефолтного `staleTime` (у TanStack Query он `0` по умолчанию), так
что _каждый_ повторный визит на уже загруженный интервал запускал
фоновый рефетч, даже несмотря на то, что сам рендер приходил из кэша
мгновенно — формально это был провал требования "без сетевого запроса",
не только его духа. Исправлено глобальным `staleTime: 30_000` — почему
30с и почему глобально, а не по каждому запросу — см. комментарий в
самом `main.tsx`.

**Настоящий зависший бэкенд, найденный случайно, не специально.** Запуск
`npm run lighthouse` (3 полных загрузки страницы) одновременно с
отдельным Playwright-скриптом, бьющим по тому же локальному
`market-analyzer serve`, заморозил бэкенд посреди запроса — TCP
подключился, запрос ушёл, ответа не было никогда (подтверждено свежим
`curl` спустя 7+ минут). Перезапуск процесса бэкенда сразу всё вылечил, и
дальше он оставался здоровым под повторными последовательными запросами.
Это забота бэкенда (бэкенд был уже полностью готов до начала этой
работы над фронтендом), упомянуто здесь как настоящая находка из
тестирования, а не потому что что-то ниже это чинит: **не гонять
Lighthouse и отдельный browser-automation-скрипт по одному и тому же
локальному бэкенду одновременно.**

**Баг в самом наборе перф-тестов, найденный самостоятельно при
добавлении новых замеров fps/памяти.** `playwright.config.ts`'s проект
`chromium-perf` унаследовал верхнеуровневый `fullyParallel: true`. Пока в
этом проекте был только один тайминг-чувствительный тест (рендер 50 000
свечей), это не имело значения. Добавление ещё четырёх в тот же файл
сделало его значимым немедленно: запуск всех 5 как параллельных
worker-процессов сталкивает их в конкуренцию за CPU _друг с другом_, и
тест на рендер 50 000 свечей — не тронутый, раньше стабильный — начал
падать на 406мс против своего бюджета в 200мс чисто из-за этой
конкуренции. Исправлено установкой `fullyParallel: false` именно для
проекта `chromium-perf` (проект `chromium` не тронут и по-прежнему
полностью параллелен), так что тесты этого файла теперь идут один за
другим в одном worker'е.

**DuckDB-WASM: не реализован.** Локальный ресемплинг через DuckDB-WASM
был опциональной возможностью, и ни одна функциональная часть
приложения от него не зависит — весь ресемплинг/агрегация, нужные этому
приложению, уже происходят на сервере. Добавление WASM query-движка на
клиенте ради нуля обязательной функциональности было бы объёмом за
пределами необходимого.

### Известное и важное на будущее

- **`unwrap()` перед `.map()` по данным графика.** `props.data` у
  `PriceChart` в конечном счёте приходит из `@tanstack/solid-query`,
  чьи данные — Solid-стор (реактивный прокси). Профилирование показало:
  чтение 5-8 полей на 50 000+ строк через прокси стора съедает
  ~450 мс, при бюджете в 200 мс на весь первый рендер. Любой новый
  код, который делает объёмный проход по данным из
  `createQuery`/`createStore` вне JSX (не точечное реактивное чтение
  поля), должен явно звать `unwrap()` из `solid-js/store`.
- **Вторичные оверлеи — в `requestAnimationFrame`, не в критическом пути.**
  MA(20) добавляет свой собственный `LineSeries.setData()` — ещё один
  проход по всем барам вдобавок к свечам и объёму. Инлайново это добавляло
  ~50-70 мс к первому рендеру, чего хватало, чтобы 50k-свечной сценарий
  вылетал за 200-мсный бюджет рендера. `price-chart.tsx` считает и
  применяет MA одним кадром позже — то же правило будет нужно для любого
  следующего оверлея на основном графике.
- **Синхронизация зума (`charts/sync.ts`) публикует только настоящие
  жесты пользователя.** И Lightweight Charts, и uPlot зовут свой
  "видимый диапазон изменился" колбэк не только на реальном
  драге/зуме, но и на программном `setData()`/собственном
  автомасштабировании при монтировании. Если публиковать это в общий
  синхросигнал безусловно — какая панель домонтировалась/дозагрузилась
  последней, молча перетирает вид всем остальным (воспроизведено:
  автомасштаб только что смонтированной панели индикатора отменял
  `fitContent()` основного графика через мгновение после корректного
  рендера). `trackUserGestures` отслеживает реальные
  `pointerdown`/`pointermove`/`wheel` на элементе графика и пропускает
  публикацию, если рядом не было такого события — работает одинаково для
  обеих библиотек графиков.
- **uPlot не умеет зум колесом из коробки** — только драг-выделение
  (`cursor.drag.x`). Тестировать синхронизацию зума с панели нужно драгом,
  не `mouse.wheel`.
- **`/analytics/{symbol}/anomalies` не даёт непрерывный ряд z-score** —
  только строки, где z-score превышает `threshold`, и бэкенд отклоняет
  неположительный `threshold`. Панель "Volume Z-Score" поэтому рисует
  разрозненные маркеры (`style: 'points'`), а не выдуманную сплошную
  линию — это честное отражение того, что даёт эндпоинт, не баг.
- `SymbolPicker` — полноценный combobox: клавиатурная навигация
  (`ArrowUp`/`ArrowDown`/`Enter`/`Escape`, ARIA
  `combobox`/`listbox`/`option`), недавно использованные символы первыми
  при пустом фильтре (`src/state/recent-symbols.ts`, `localStorage`, до 6
  штук), `data-hotkey-target="symbol-search"` для `/`-хоткея.
- DuckDB-WASM — не реализован, см. раздел "Производительность и
  доступность" выше — он был опциональной возможностью, и ни одна
  функциональная часть приложения от него не зависит.
- **Бюджет JS-бандла закрыт через прогрессивный `lazy()`, а не разовую
  чистку.** В какой-то момент прод-сборка ушла за бюджет (150.93 КБ
  gzip JS из 150 КБ). Закрыто по одному компоненту за раз, с перемером
  после каждого: `CorrelationMatrix` → `AnomaliesTable` → `OfiPanel` →
  `TradeTape`, через `lazy(() => import(...))` +
  `<Suspense fallback={<PanelSkeleton />}>` (`src/ui/skeleton.tsx`) на
  месте использования; каждой цели нужен `export default` (`lazy()`
  только с ним и работает). Итог — 143.36 КБ из 150 КБ, с запасом, а не
  "еле прошло". Первые три — выключены по умолчанию (`OFI`/`Correlation`
  — чекбоксы, `Аномалии` — не дефолтная вкладка сайдбара) — очевидные
  кандидаты. `TradeTape` — тоньше: это **дефолтная** вкладка сайдбара, но
  у неё нет исторического REST-эндпоинта (только живой поток), так что
  она пустая независимо от скорости загрузки чанка — задержка на
  подгрузку чанка тут строго дешевле, чем ожидание первой сделки в любом
  случае. (Тема/палитра/CSV-кнопка позже добавили ~4.5 КБ в вечный
  чанк — 147.85 КБ из 150, запас уже не такой, как был; дальнейший рост
  почти наверняка снова потребует либо новый `lazy()`, либо пересмотр
  того, что уже в вечном чанке.)
- **Баг в собственном `scripts/check-bundle-size.mjs`, всплывший ровно от
  появления `lazy()`.** Раньше скрипт суммировал gzip каждого `.js`/
  `.css` под `dist/assets/` — корректно, пока не было кодосплиттинга.
  После первого же `lazy()`-выноса (`CorrelationMatrix`) скрипт
  продолжал считать превышение бюджета, хотя вынесенный чанк специально
  не должен грузиться на первом экране. Причина — скрипт складывал
  вообще все файлы в `dist/assets/`, включая lazy-чанки, в "начальный"
  бюджет. Исправлено: скрипт теперь парсит сами `<script
src>`/`<link href>`-теги в `dist/index.html` (то, что браузер реально
  грузит eagerly на первом экране) и меряет gzip только этих файлов —
  lazy-чанк, ещё не запрошенный, в этот бюджет не входит по определению.
- **`createSeriesMarkers` (Lightweight Charts) рисует на тот же `<canvas>`,
  что и свечи — снаружи никакого запрашиваемого состояния нет.** Для
  сценария "клик по аномалии → прыжок графика к бару с маркером" e2e-тест
  не может проверить "прыжок применился" через DOM/API графика — там
  нечего читать. Решение — не мок внутреннего состояния и не пропуск
  теста, а один постоянный атрибут `data-last-jump-nonce` на корневом
  `div` `PriceChart` (`src/charts/price-chart.tsx`), который меняется в
  том же эффекте, что двигает `timeScale()` и зовёт `markers.setMarkers()`.
  Тест просто ждёт, что атрибут изменился — не заглядывает во
  внутренности графика.
- **Порог/окно у таблицы аномалий — дебounced через сигнал +
  `window.setTimeout`, не через сторонний хук.** Сырой сигнал инпута и
  "подтверждённый" сигнал (тот, что реально уходит в `queryKey`)
  разведены, синхронизация — в `createEffect`, который сбрасывает и
  переустанавливает таймер (300мс), с очисткой через `onCleanup`. Такой же
  паттерн — кандидат для любого следующего дебounced-контрола, отдельная
  библиотека под это не нужна.
- **Матрица корреляций красит ячейки через CSS `color-mix()`, поверх уже
  существующих семантических токенов** (`--color-up`/`--color-down`/
  `--color-surface`), а не новой цветовой шкалой — диврегирующий градиент
  получается без единого нового токена. Цвет и здесь не единственный
  носитель информации — числовое значение корреляции лежит текстом в
  каждой ячейке независимо от цвета.
- **Тест на "хоткеи не должны срабатывать при вводе в поле" сам себя чуть
  не обманул.** Первая версия стартовала с интервала, который "стреляющий
  мимо guard'а" хоткей (`1` → `1m`) всё равно бы дал — то есть тест прошёл
  бы что при рабочей защите от тайпинга, что при полностью сломанной.
  Пойман до первого запуска, просто перечитыванием теста: старт на другом
  интервале (`15m`) делает поломку guard'а наблюдаемой (URL обратно
  скакнул бы на `1m`). Общий урок для будущих хоткей-тестов: стартовое
  состояние должно быть таким, чтобы баг и работающий код были
  различимы, а не просто "тест технически проверяет что-то".
- **`page.routeWebSocket` — не `page.route`.** Плейрайт мокает HTTP через
  `page.route`, но WS-соединения им не перехватываются вообще — нужен
  отдельный `page.routeWebSocket(pattern, ws => ...)` (см.
  `tests/e2e/live-stream.spec.ts`). Даёт `ws.send()`/`ws.close()` — этим
  снят по-настоящему реальный e2e для сценария "форс-обрыв → реконнект →
  данные без разрыва", не просто юнит-тест на бэкофф-таймер.
- **`npm run lighthouse` не находит Chrome сам по себе в этом окружении.**
  `@lhci/cli`'s healthcheck ищет системный `google-chrome`/`chromium`,
  которого тут нет — есть только тот, что уже скачал себе Playwright.
  Экспортировать `CHROME_PATH` перед запуском:
  `CHROME_PATH=$(node -e "console.log(require('playwright-core').chromium.executablePath())") npm run lighthouse`.
- **Не гонять `npm run lighthouse` параллельно с чем-то ещё, что бьёт по
  тому же локальному бэкенду.** См. "Производительность и доступность"
  выше — реальный зависший бэкенд, воспроизведённый именно так.

### Фронтенд

Юнит-тесты (`vitest`) лежат рядом с кодом (`src/**/*.test.ts`):
Arrow-парсинг проверен на побитово том же layout колонок, что и
`ma_api::arrow_ipc::ToRecordBatch` (`crates/api/src/arrow_ipc.rs`) —
`src/api/arrow.test.ts` гоняет реальный `apache-arrow` IPC round-trip, не
мок. `src/api/client.test.ts` покрывает fallback-логику и разбор ошибок
API. `src/charts/indicators.test.ts` — клиентский MA(20).
`src/stream/socket.test.ts` разбирает WS-фреймы, реально снятые с
локального бэкенда (не выдуманные), включая точный формат сообщений
(`type`/heartbeat). `src/stream/buffer.test.ts` — rAF-батчинг и
переполнение буфера. `src/panels/stats.test.ts` — чистая функция
подсчёта 24ч-изменения/объёма для строки состояния (в т.ч. `null`, а не
`0`, когда в окне нет баров или текущая цена ещё не известна — эти два
случая размечены разными полями, не совпадением с нулём).
`src/export/csv.test.ts` — CSV-форматтер, без DOM (только
`buildOhlcvCsv`, не `downloadCsv`). `src/panels/correlation-matrix.test.ts`
— `correlationColor()`'s 50%-cap на блендинг цвета (см. про контраст
выше).

E2E-файлы Playwright (`tests/e2e/*.spec.ts`) typecheck'аются отдельным
`tsconfig.e2e.json`, не общим `tsconfig.node.json` — `page.evaluate(() =>
...)`'s callback _source text_ здесь на самом деле выполняется в
браузере, который Playwright водит, а не в Node, и ему нужен `lib: DOM`
(`window`, `requestAnimationFrame`, `PerformanceObserver`'s `'longtask'`
entry type) — которого нет и не должно быть у остальных Node-контекстных
файлов (`vite.config.ts` и т.п.), делящих `tsconfig.node.json`.

E2E (`tests/e2e/`, Playwright) мокает `/symbols`, `/analytics/*` и
`/ohlcv/*` через `page.route` (WS — через `page.routeWebSocket`, см. выше)
— реальный бэкенд не нужен
(`tests/e2e/fixtures.ts` строит настоящие Arrow IPC байты того же формата,
что и бэкенд). Моки `/ohlcv/*` учитывают `limit`/`offset` и `to` так же,
как настоящий бэкенд — иначе догрузка истории при скролле на маленьком
фикстурном наборе тут же ловит несогласованность порядка по времени
(сама догрузка при этом отработала корректно; несогласованной была ровно
неосведомлённая о датах заглушка). `tests/e2e/analytics-panels.spec.ts`
— клик по аномалии двигает график (через `data-last-jump-nonce`, см.
выше), падение одного аналитического эндпоинта не роняет остальные
панели (мок 500 на VWAP), хоткеи `1`-`6`/`/`/`Esc` и то, что хоткеи не
стреляют во время печати в поле поиска. `perf.spec.ts` (все замеры
производительности из раздела выше) идёт отдельным Playwright-проектом
(`chromium-perf`) против прод-сборки (`vite build` + `vite preview`), не
против dev-сервера — тот же принцип, что у Lighthouse CI. Этот проект
специально не полностью параллелен (`fullyParallel: false` в
`playwright.config.ts`) — все пять тестов в файле тайминг-чувствительны,
и конкуренция за CPU между ними искажала измерения (см.
"Производительность и доступность" выше).

Первый запуск `npm run test:e2e` подтягивает браузер Chromium сам по себе
через Playwright; в песочнице без `sudo` `playwright install --with-deps`
не сработает — обычный `npx playwright install chromium` (без
`--with-deps`) собственных системных зависимостей не ставит и обычно
работает, если они уже есть в системе.

## Известные ограничения

- REST-добор сделок после реконнекта идёт через `aggTrades` (у Binance нет
  time-ranged эндпоинта для сырых сделок) — id добранных строк в пространстве
  aggTradeId, не совпадает с id живого потока (дублей не даёт, но это не то
  же самое ID-пространство).
- `WS /stream/{symbol}` открывает отдельную подписку на Binance на каждого
  подключённого клиента (не мультиплексируется). Поэтому число
  одновременных клиентов ограничено `MA_API_MAX_WS_CONNECTIONS` (по
  умолчанию 64) — сверх лимита новые подключения получают `429`.
- Полный 12-часовой прогон `stream` без утечек памяти не воспроизведён в
  рамках разработки (см. `BENCHMARKS.md`) — 8-минутный прогон на 20 символах
  показал здоровый профиль (~105 МБ из бюджета 512 МБ), но это не то же
  самое, что 12 часов.
- Часть контракта с фронтендом ещё не реализована на бэкенде: HTTP-кэш-
  заголовки для `/ohlcv`/`/analytics/*` и `price_precision`/`qty_precision`
  в `/symbols` — добавляются по мере необходимости фронтенду. Arrow IPC,
  CORS и тип события в WS (`type`+heartbeat) уже готовы.
- `vwap`, `volatility` и `anomalies` (CLI и HTTP) сканируют всю историю
  символа/интервала под своим скользящим окном — `from`/`to` для них не
  предусмотрены. Корректно ограничить диапазон без порчи статистики у
  границ скользящего окна требует отдельного редизайна (pushdown `to`
  безопасен, `from` можно применять только к выводу, LIMIT/OFFSET для
  window-функций нужна обёртывающая SELECT); на объёмах, которые собирает
  этот сервис сейчас, не является узким местом. `/analytics/correlation`
  ограничен 10 символами (см. выше) — единственный из аналитических
  запросов с O(n²)-стоимостью.
